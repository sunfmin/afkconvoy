afkconvoy works a repo's ready GitHub-issue backlog unattended. A fleet instance — one
`afkconvoy run` — dispatches one worker per issue, a coding agent isolated in its own git
worktree, and lands each finished PR on the base branch through the landing train, behind
the gate. Fleet state lives entirely in GitHub and the repo's remote: no process holds it.

This text is the way in. What it leaves out is in each command's own help.

WHAT IT NEEDS

  - A config on the base branch: the first yaml block of docs/agents/afkconvoy.md.
  - `gh` logged in as a user who may push to the repo.
  - `orca` on the PATH: every worker is started through it. It is running (`orca open`)
    and was given this checkout, once (`orca repo add --path "$PWD"`).
  - `claude` on the PATH and logged in, when it is what starts a worker.

  `plan`, `tick` and `run` check these first. With one missing, logged out, not running
  or not given the checkout they do nothing and the error gives the line to run for
  each: nothing is installed, started or added for you.

WHAT TO RUN FIRST, in a checkout of the repo

  1. afkconvoy config    Read the config: what the fleet goes by.
     afkconvoy check     Only where the config names a team: does the team load?
                         A team is designed first: DESIGNING A TEAM, below.
  2. afkconvoy plan      What a tick would act on. It changes nothing.
  3. afkconvoy run       The fleet instance: tick after tick, until stopped.

  And whenever something looks wrong: afkconvoy doctor — it reads everything, changes
  nothing, and names the fix of each thing it finds.

WHAT A COMMAND ANSWERS

  Every command prints exactly one JSON object on stdout. A failure is {"error": …} with
  a non-zero exit. Warnings go to stderr. `run` instead prints one line per tick until
  it is stopped, `show` a drawing unless it is asked about an issue, and `guard` answers
  the harness that asks it as a hook does: with its exit code.

THE COMMANDS, by who runs them

  Read `afkconvoy <command> --help` before the first time you run one.

  The operator — starting, watching or stopping a fleet. Read these first. `doctor` is
  what to run when something looks wrong, or you are asked whether the fleet is working:
  it says what the fleet on this host is doing and what is wrong, each finding with the
  line that fixes it:
      doctor  config  check  plan  run  panel  tick  takeover

  Whoever designs a team — `scaffold` to start one or a role of it from a skeleton,
  then, once `check` accepts it, the others: to review a workflow, to try one out with
  no worker started, or to ask where an issue is in its workflow:
      scaffold  show  rehearse

  Whoever hands the fleet work — a human, or the agent a human is talking to, with work
  decided on and issues to open for it. Read it before opening the first: it says which
  workflow takes which issue and the line that opens one, and creates the labels:
      flows

  A worker — its prompt names each one as it is needed. Read them only when you are a
  worker, or are finding out why one stopped (`rule`, below, is a consult's too):
      gate  land  verdict  intake  lock  over  wake

  A human an issue waits for — in a bound repo. Read them to answer an escalated issue,
  to put an issue at a stage of your choosing, or to see what a `by: human` stage asks:
      rule  send

  A worker's hook — its harness asks it before each thing a bound repo's worker does.
  Nobody runs it by hand. Read it to learn what a worker is refused, and why one was:
      guard

  One transition by hand — each is something a tick does on its own. Read one when a
  plan shows a transition the fleet is not making, or you are told to make it yourself:
      dispatch  recovery  close  escalate  park  nudge  restart  abandon

  The claim plumbing — what the transitions are built on. Read these only to inspect or
  repair claims and heartbeats on the remote:
      scan  claim  release  heartbeat

RULES TO KNOW BEFORE YOU START

  - One fleet instance per host per repo. A second `run` on a host takes the first
    one's claims: never start one beside a fleet that is running.
  - `run` never returns. Do not wait on it: start it in the background and read its
    lines, or use `tick` for one pass that exits.
  - With a custom provider (ANTHROPIC_BASE_URL set) and no terminal, a command that
    starts a worker needs `--worker-command`: there is nobody to ask.
  - A fleet instance has one worker launch command for each harness its workers run.
    `--worker-command <command>` says the default harness's, and
    `--worker-command <harness>=<command>` one harness's, by its key: once for each.
    A harness nobody said one for is started with its stock command.
  - In a bound repo the worker launch command must end in its harness — Claude Code,
    or pi — taking flags: the fleet adds to it what starts each worker in its role and
    under the guard, and a start refuses a command whose `--help` does not name those
    flags. Every harness the team could ask for is checked before any worker is
    started, and none is ever started in another's place. What each harness's worker
    is started with: `afkconvoy run --help`.

DESIGNING A TEAM, for a bound repo

  A repo whose config names a team — `team: owner/repo`, or `team: owner/repo/path` for
  a team in a subdirectory — is a bound repo. An issue of
  it that carries a flow label is walked through that workflow's stages, each performed
  by a new worker started in the stage's role. A team and a role are each a directory of
  text files — a whole repo, or a subdirectory of one, so that one repo can hold a team
  and every role it names — and designing one is editing them. Nothing else holds any of it.

{files}

  The loop, from nothing:

  1. afkconvoy scaffold role <dir> --repo <owner/repo>
       A role's skeleton, created on GitHub: `check` reads a role from there only.
  2. afkconvoy scaffold team <dir> --role <name>=<owner/repo>
       A team's skeleton, with one workflow which that role performs.
  3. afkconvoy check --dir <dir>
       Edit a file, run it, and read the faults: each names its file and key. Repeat
       until it exits 0. A role's edit counts once it is pushed to its default branch.
  4. Push the team, name it under `team` in the config, and run `afkconvoy check` in
     that checkout. Then `show` draws each workflow and `rehearse` tries one out.

  A role's skills are added with the skills installer you already use, run in a checkout
  of the role's repo and committed there, so that every host runs the same role. The
  fleet installs no skill and wraps no installer.
