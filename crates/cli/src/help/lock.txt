WHEN TO RUN IT

  When the fault is one every issue shares — the base branch is broken, so every gate
  is red whatever its PR holds — and one issue carries the fix. Raise the lock on that
  issue:

      afkconvoy lock --issue 7

  From the next tick the fleet works lock issues only, until the last of them closes.
  For anything that is wrong with one issue alone, declare a verdict instead.

WHO RUNS IT

  A worker, in its own worktree: a patrol that finds the base branch red, or a stage
  that finds it cannot be the only one to fail. The operator may run it too, in a
  checkout of the repo; a human may as well put the lock label on the issue on GitHub.

WHAT IT READS AND WRITES

  It reads the issue and the config's `lock_label` (default fleet-lock). On an open
  issue that does not carry the label it writes one comment — the record of the role
  that raised the lock, read from `--role` or from the worker's environment
  (AFKCONVOY_ROLE); a worker of an unbound repo has none — and then puts the label on
  the issue. Then it wakes the fleet, as `afkconvoy wake` does.

  It claims nothing and starts nothing. The lock issue is worked as any issue is: in a
  bound repo once it carries a flow label, in an unbound one once it carries the ready
  label. Nothing here takes a lock off: closing the issue ends it — landing the PR
  that closes it does.

WHAT IT ANSWERS

  {"issue", "label", "role", "raised", "locks", "woke"}

    label          the lock label the issue now carries
    role           the role on record as having raised it, or null
    raised: true   the record was written and the label put on
    raised: false  the issue was a lock already: nothing was written
    locks          every fleet lock standing now, lowest number first
    woke           whether a `run` on this host was told, as `afkconvoy wake` answers

  Errors, as {"error": …} with a non-zero exit: the issue is closed; there is no such
  issue; the config cannot be read; "is not in a git checkout".

WHAT TRIPS YOU UP

  - A lock stops everything else, on every host: no other issue is dispatched, no
    stale claim of another issue is taken, no issue is handed to a human, and no PR of
    another issue joins the landing train (`afkconvoy land` answers `locked`).
  - Workers already running are left alone, and nobody asks after them: what they
    declare — a verdict, a PR — is acted on once no lock stands. Their claims take no
    slot meanwhile, so a lock issue is started even by a fleet at its bound.
  - What was on the landing train before the lock is not taken off it. The lock
    issue's PR joins behind it.
  - A lock issue nothing makes dispatchable — no ready label, no flow label, an epic
    label, an open blocker — is worked by nobody, and the lock stands all the same.
    `afkconvoy plan` shows the lock under `locks` and the issue under `excluded`,
    with why.
  - It does not check that the base branch is broken. It is refused to nobody: the
    guard recognises the label being moved by hand, not this command.
