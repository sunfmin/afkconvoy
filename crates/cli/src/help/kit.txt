WHEN TO RUN IT

  Run `afkconvoy kit` at a terminal before starting workers on a new host, to
  change how this host starts a harness, or to probe its models again. It needs
  no repo and changes no remote.

WHO RUNS IT

  The operator, at a terminal on the host that starts the workers.

WHAT IT READS AND WRITES

  The host kit is $XDG_CONFIG_HOME/afkconvoy/kit.json, or
  $HOME/.config/afkconvoy/kit.json when XDG_CONFIG_HOME is unset. It is kept on
  this host and never pushed. It is the only source of worker launch commands.
  It holds the harnesses this host can start, in order of preference, each with
  its worker launch command and the models it was seen to answer with, in
  order; and the harness and model of the stock consult.

  1. Commands. With no kit it finds every known harness program installed on
     PATH and proposes its stock worker launch command. With a kit it shows the
     saved commands. For each harness, Enter keeps it, a typed command edits or
     adds it, and - drops it.
  2. Models. Each harness kept is asked through its command for the models it
     offers (pi, Codex); one the fleet has no way to ask (Claude Code, DSH) is
     shown so. Enter probes the models shown — the kit's, then those offered —
     typed names probe those instead, and - probes none.
  3. Probes. Each model is sent a one-line prompt in the login shell a worker
     gets, at most 60 seconds each, eight at a time. It shows which answered
     and how long each took. Only those that answered are written, with when.
     DSH can be sent no prompt but in a worker's terminal: its models are held
     unprobed, as named.
  4. Order. Type the harnesses, then each harness's models, first first; any
     left out follow in the order shown. Enter keeps the order shown. The
     first harness and its first model are the host kit's first.
  5. Stock consult. Type a harness and, optionally, one of its models to name
     what the stock consult runs; - or nothing named runs the host kit's first.

  6. What each model is good at. Write `"good_at": "<a few words>"` beside a
     model in the file by hand: a caster is told it (`afkconvoy cast --help`).
     Editing the kit again keeps it.

  It shows the proposed kit and writes only after you answer y or yes. Declining or
  end of input writes nothing. A kit needs a terminal; there is no automatic yes.

WHAT IT ANSWERS

  {path, written, kit}: the file, whether it was written, and the kit when
  written. Errors: no terminal; a kit that cannot be read or written.

WHAT TRIPS YOU UP

  `run` asks for this same setup at a terminal when no kit exists. Without a
  terminal it refuses and names `afkconvoy kit`. Other commands never ask.
  A missing harness is refused before workers start; it has no implicit stock
  command. `--worker-command` is gone: edit the host kit with `afkconvoy kit`.
  A command is an opaque shell string; an unbound repo starts it as written,
  under nice with its worktree's TMPDIR, adding only its harness's model flag
  for the model an issue's casting, the host kit's first or the stock consult
  names. A bound repo adds its role flags.
  Probing sends each model a real prompt: it spends a little of each login.
