WHEN TO RUN IT

  After every edit to a team's files, a role's skills or a repo's `team` key, and before
  a fleet is started on a bound repo: it says whether the team loads, and if not, every
  fault at once. Edit, run it, and repeat until it exits 0.

WHO RUNS IT

  The operator, or whoever designs the team: in a checkout of a bound repo, or anywhere
  with `--team` or `--dir`.

WHAT IT READS AND WRITES

  It writes nothing but a copy the fleet has not got yet (below), and what this host
  keeps for pi and for Codex before each is asked a question (`afkconvoy run --help`).
  It reads a
  team's files, and of each role's directory which skills it holds and what each one's
  `SKILL.md` opens with, which harnesses it holds limits for, and whether a file of it
  would have a harness load other rules.
  What those files are, and every key of each: `afkconvoy help team`,
  `afkconvoy help workflows` and `afkconvoy help patrols`.

  Without a flag it reads the config of this checkout for `team`, and that directory
  from GitHub at the head of its repo's default branch — and holds the config's
  `patrols` against the patrols that team has, and takes its `harness` as the default.
  `--team owner/repo` or `--team owner/repo/path` names the team instead.
  `--dir <path>` reads a team's files from a directory as they are, committed or not.
  Every role is always read from GitHub, at the head of its repo's default branch. A
  directory says no repo, so a role it names as `./path` is a fault — unless `--team`
  beside `--dir` says which team on GitHub the files are an edit of: the role is then
  read from that repo.

  A repo on GitHub — the team's, and each role's — is asked for the commit at its head,
  and read from the fleet's copy of that commit: the one a worker's directory is taken
  out of, kept
  read-only under the cache directory (copies/<owner>/<repo>/<commit>): `afkconvoy help
  cache` says where that directory is on this host, and what moves it.
  Only a commit the fleet has no copy of yet is cloned, so a role pushed since the last
  run is read at its new head, and one that has not moved costs one question. A repo is
  asked and cloned once however many roles it holds, and a role in the team's own repo
  is read at the team's commit. The repos are read at once, not one after another.

  Where the team names a `model`, each harness that can say which models it knows is
  asked, in a login shell — the one a worker gets — under the user directory the fleet
  keeps for it. pi, with `pi --list-models`: it lists the models pi has a login for on
  this host. Codex, with `codex --dangerously-bypass-approvals-and-sandbox debug models
  --bundled`, its stock worker launch command: it lists the models this host's Codex was
  built with, each by its `slug`, and asks no network. Claude Code has no such answer,
  and is asked nothing.

WHAT IT ANSWERS

  {"team", "path", "commit", "files", "escalate_label", "rules", "host_user", "dsh_profile", "split", "harness",
  "roles", "workflows", "patrols", "precedents"} — what it read.
  `team` is the team's repo and `path` its directory there, "" for a whole repo — with
  `--dir`, the directory read and null. `commit` is the team's commit read, null with
  `--dir`; `files` the definition files read, each from the team's directory.
  `rules` is whether the team has rules of its own: a `CLAUDE.md` in its directory,
  which every one of its workers is given.
  `host_user` is whether its workers are given the host user's own skills and rules
  beside their role's: true unless the team file says `host_user: false`, and a value
  that is not true or false is a fault (`afkconvoy help roles`). It is each role's
  default, and the stock consult's.
  `split` is whether stage briefs offer splitting: true unless the team file says
  `split: false`. Anything but true or false is a fault (`afkconvoy help team`).
  `harness` is the default harness: the one the config of this checkout names, and
  claude-code where it names none — and with `--team` and `--dir`, which read no
  config. Each of
  `dsh_profile` is `fleet` (default) or `host-user`: which profile DSH workers
  load, independently of host_user. A role may override the team's choice; check
  answers its effective dsh_profile and refuses every other value.

  `roles` is {"name", "repo", "path", "commit", "host_user", "dsh_profile", "skills", "above",
  "limits"}: `path` is the role's directory in `repo`, "" for a whole repo; `commit` the
  one the role's repo was read at; `host_user` whether its workers are given the host
  user's skills and rules — its own say, `{ dir, host_user, dsh_profile }`, or the team's; a key of
  that map but those three, or a `host_user` that is not true or false, is a fault;
  `above` each `CLAUDE.md` and `.claude/` a directory above the role holds in its repo, as a path from the repo's root — but for the team's own `CLAUDE.md`,
  where the team's directory is above the role: those are the team rules, which a
  worker is given; `limits` the harnesses the role holds
  limits for — a hook or a denied permission in its `.claude/settings.json` for
  claude-code, an entry of its `.pi/extensions/` for pi, a hook in its
  `.codex/hooks.json` for codex, a `.dsh/cordis.patch.yml` overlay for dsh. Each of `workflows` is {"name", "flow_label", "max_rework",
  "max_consecutive_rework", "stages", "land"}, the defaults filled in; each stage is
  {"name", "by", "do", "harness", "model", "writes", "escalate", "pass", "reject"}.
  Each of `patrols` is {"name", "by", "do", "every", "harness", "model", "max_open",
  "max_runs_a_day", "max_landed_a_day", "runs_here"}: `every` in seconds, `max_runs_a_day` null where the
  file says none. A `harness` is the one the stage's worker, or the
  patrol's, runs: the one it names, or the default — and null of a stage a human
  performs. `runs_here` is whether the config of this checkout names the patrol — false
  with `--team` and `--dir`, which read no config. `precedents` is {"by", "do",
  "max_open"}, or null where the team names nobody to propose them.

  A team with a fault: {"error", "faults"} and exit 1. `faults` holds every fault of the
  team, not the first: each {"file", "key", "problem", "see"}. `key` is a path from the
  top of
  the file's yaml, counting from 0 — `stages[1].on.reject` — and empty when the fault is
  the file itself. `see` is the command that prints the help topic describing that file,
  to run as it is: `afkconvoy help workflows` for a workflow's, `afkconvoy help patrols`
  for a patrol's, and `afkconvoy help team` for the team file — a role is named there,
  and that topic says what its directory holds — and for the config's keys that bind the
  repo. A fault in a file no topic describes has no `see`.

  A fault is one of: an unknown key, or one written twice; a wrong
  type; a duplicate stage name; a stage named `land`, `done` or `human`; a `pass` or
  `reject` that names no stage; a `reject` to its own or a later stage; a stage no path
  from the first reaches; a stage whose passes never come to `land` or `done`; a
  `pass: land` with no `land:`, or a `land:` no pass leads to; a role the team file does
  not name; a role named as none of owner/repo, owner/repo/path and ./path; a role's
  path with a `..`, or an absolute one; a role whose repo cannot be read, or whose path
  is no directory at its head; a role's directory that is the team's or contains it, or
  is inside the team's `workflows/` or `patrols/`; a role's directory that contains
  another role's or is inside one — two names for one directory are none; a symlink in
  a role in a subdirectory that leaves the role's directory; a file in a role's
  directory that a harness would load in place of `CLAUDE.md`, its rules under every
  harness — pi `AGENTS.override.md`, `AGENTS.md` or `AGENTS.MD`, Codex
  `AGENTS.override.md` or `AGENTS.md` — the fault naming the file and each harness
  that would load it, whatever harness the role's stages run on; a role's limits that cannot be
  read; a skill its role's directory does not hold; a
  missing `by`, `do` or `on`; a `harness` that names no harness, or one on a stage a
  human performs; a flow label two workflows take, or one that is the team's escalate
  label, the repo's lock label or an epic label — under `label`, or the file where it
  is the `flow:<name>` it names none in place of; a patrol file whose name is not a patrol's; an `every`
  that is no duration; a missing `every` or `max_open`; and — in the config,
  docs/agents/afkconvoy.md, under `patrols` — a name the team has no patrol for.

  A team that loads is then held to its harnesses, and these are faults too, each with
  its file and key, all at once:

  - A skill a worker is asked to perform whose file is not in the form every harness
    reads a skill in: its directory holds no `SKILL.md`, or one that opens with no
    frontmatter, or whose frontmatter says another `name` than the directory's, or no
    `description`. The key is the `do` that names the skill — `stages[1].do`,
    `stages[1].escalate.do`, `land.do`, a patrol's `do`, and `precedents.do` in
    team.md — and each `do` that names it has the fault. The form is in
    `afkconvoy help skill-file`. A skill no `do` names is not held to it.
  - A worker on a harness its role holds no limits for, while the role holds limits for
    another: the fault names what runs it, the role and both harnesses. Its key is the
    `harness` of the stage (`stages[1].harness`) or of the patrol, written there or
    not; for a worker that always runs on the default, the key that names its role —
    `stages[1].escalate.to`, `land.by`, and `precedents.by` in team.md. A role with no
    limits at all is no fault.
  - A `model` its harness does not know, where the stage or the patrol names that
    harness and the harness could be asked: the key is the `model`. pi knows a model
    it lists by its `provider/id`, its id or a part of its id, with a thinking level
    after a `:` or not. Codex knows a model by the whole `slug` it lists it under, as
    written, and no other way: the ones it shows in no menu are among them. A model
    named for a harness that cannot say — claude-code — or could not be asked, or that
    listed nothing, is passed as written.
  - In the config, docs/agents/afkconvoy.md, under `harness`: a team that names models
    and no harness for them, none of which the repo's default harness knows. Such a team
    is written for another default; the fault lists each model and what names it.

  A warning, on stderr, for each workflow whose file says nothing above its yaml block:
  that prose is what `afkconvoy flows` answers as what the workflow is for, and whoever
  hands the fleet work chooses a workflow by it. The team loads all the same.

  A warning, on stderr, for each model named with no harness that reads as another
  harness's — pi's whole `provider/id` for a model it lists, or a `slug` Codex lists —
  while the default harness said nothing of which models it knows: the team may be
  written for another default. And a
  note for a harness a model is named for that could not be asked: its command failed
  in a login shell, or listed no model. The team loads all the same.

  A note, on stderr, for each role with something in `above`: a session opened by hand
  in the role's directory loads those rules too, and a worker, given the role's
  directory alone, does not. The team loads all the same, and it exits 0.

  A note, on stderr, for each worker on codex whose role holds an `.agents/skills/` or
  a `.codex/skills/` itself, the skill the worker is asked to perform not in either:
  Codex finds skills there and not in `.claude/skills/`, the fleet leaves what a role
  holds there as it is, and the worker would not be shown that skill. A role that holds
  neither is given a link to its skills, in the fleet's copy, and nothing is noted. The
  team loads all the same, and it exits 0.

  A note, on stderr, for a team whose directory holds a `.claude/`: the hooks and skills
  there are loaded by no worker. Of a team's directory a worker is given the rules, and
  a hook and a skill are a role's. The team loads all the same, and it exits 0.

  Other errors, as {"error": …}: the repo's config names no team and no flag was given;
  the config cannot be read, the error naming its file and the key — a `harness` there
  that names no harness is one; the team's repo cannot be read, or the team's path is no
  directory at its head.

WHAT TRIPS YOU UP

  - From GitHub it reads what is pushed to the default branch. An edit in a checkout
    of the team is checked with `--dir`; a role's is checked only once it is pushed,
    wherever the role is — in the team's own repo too.
  - Which models pi knows is this host's answer: the ones pi has a login for here,
    asked of the stock command `pi`. Which Codex knows is this host's too: the ones the
    Codex installed here was built with, whatever it has a login for. Run `check` on
    the host the fleet runs on.
  - Only `check` holds a team to its harnesses, and a skill's file to its form: a tick
    loads the team and starts its workers without asking again.
  - Following `pass` alone from any stage must end. A loop back is made with `reject`,
    which the breakers count; a loop of passes nothing would ever stop.
  - A stage nothing leads to is reported only once every `pass` and `reject` names a
    stage: fix those first and run it again.
