WHEN TO RUN IT

  When the work is committed and before the PR joins the landing train, with `--train`;
  and again after every further commit. A worker's prompt names the exact command.

WHO RUNS IT

  A worker, in its own worktree. The operator runs it only to find out why a worker's
  gate is red.

WHAT IT READS AND WRITES

  It runs the config's `gate_command` in this worktree, its log streaming to stderr,
  for no longer than the gate limit: the config's `gate_seconds` (default 3600). A run
  that reaches it is ended, with everything it started, and is red.
  With `--train` it first merges in what the PR will land behind — the landing train's
  tip, or the base branch when nothing is on the train — a merge: nothing is rebased.
  On the remote it writes only the recorded gate run: put on record for a green run of
  a committed tree, with the seconds it took and the host it ran on (`--host`, else
  this machine's name); taken off record for a red one. It pushes no branch and changes
  nothing on GitHub; after a red run it reads which fleet locks stand.
  After the first green run in a worktree it notes, in the worktree's own git dir, what
  git ignores there as the worktree's fresh build: what `run` judges its held disk by.

WHAT IT ANSWERS

  {"status", "recorded", "detail", …}

    status       green, red or conflict
    recorded     true only when the run is on record as a pass of the commit's tree
    detail       what to do next, in words
    exit_code, timed_out, command, head
                 the run: the gate command, its exit code, and the commit it ran on.
                 A run ended at the gate limit is red, with exit_code 124 and
                 timed_out true, and `detail` says so, and what the limit is
    seconds      how long the whole gate command ran, in whole seconds, as this
                 command measured it. The fleet does not know the gate's steps: which
                 of them is slow is for the gate to print. A green run's record keeps
                 it; a red run leaves no record, and so no time
    locks        on a red run with a fleet lock standing: the locks. The base branch
                 may be what is red: declare nothing of it, stop, and run this again
                 when told to carry on
    merged       with `--train`: the commit that was merged in
    uncommitted  on a green run of a tree that was not the commit: the paths, 20 at most
    not_recorded on a green run whose record the remote refused: why
    files        on conflict: the conflicted files. No gate ran, and the merge is left
                 in progress here

  Errors: the config cannot be read; with `--train`, tracked files have uncommitted
  changes ("has uncommitted changes to tracked files"), or the remote has no base
  branch.

WHAT TRIPS YOU UP

  - A red gate is an answer, not an error: the exit is 0. Read `status` and `recorded`.
  - Green is not enough. An untracked or modified file — the gate's own artifacts
    included, unless `.gitignore` covers them — makes the run green with `recorded`
    false: it proves nothing about a commit.
  - A recorded run is of one tree. Any further commit needs another run.
  - The gate limit is no flag. It is `gate_seconds` in the config of this worktree
    (`afkconvoy config --help`), the same for a worker's run and the train's.
  - A red run is the worker's own until it shows otherwise: the commit `merged` names,
    gated alone in a clean checkout of it (this command, without `--train`), red the
    same way. Then the defect is outside its issue, and its prompt says how it records
    it: on the open issue that already does, or on one it opens — with the ready label,
    or through `afkconvoy intake` in a bound repo — and parks its issue on that one.
  - A conflict is resolved by committing the merge, then running this again. A resolved
    merge left uncommitted is refused.
