WHEN TO RUN IT

  Before opening an issue the fleet is to work, and again whenever the team gains a
  workflow: it says which workflow takes which kind of issue, what label puts an issue
  in it, and which labels to keep off — and it creates the labels that takes, so the
  line it gives works. Run it once for all the issues you open, not once per issue.

      afkconvoy flows

WHO RUNS IT

  Whoever hands the fleet work: a human, or the agent a human is talking to, with work
  decided on and issues to open for it. In a checkout of the repo the issues go to,
  bound or unbound. A worker does not: it takes an issue in with `afkconvoy intake`.

WHAT IT READS AND WRITES

  It reads the config of the checkout and the labels the repo has. In a bound repo it
  also reads the team as `afkconvoy check` does — the team's files and every role's
  repo, from GitHub at the head of each default branch — and, to count, the comments of
  every open issue that carries a flow label.

  It writes one thing: each label its lines name that the repo lacks. In a bound repo
  that is the flow label of every workflow of the team, `flow:<workflow>`; in an unbound
  one, the ready label. It puts no label on any issue and opens none. Everything is read
  first: a team with a fault creates nothing.

WHAT IT ANSWERS

  In a bound repo:

  {"team", "workflows", "keep_off", "intake", "created"}

    team         the team's repo
    workflows    every workflow of the team, each {"name", "flow_label", "description",
                 "first", "ends", "line"}:
                   description  what the workflow is for and what an issue of it holds:
                                the prose of its file, workflows/<name>.md, above the
                                yaml block. Empty when the file says nothing there —
                                `afkconvoy check` warns of that. Choose the workflow by it
                   first        the stage an issue enters at, {"stage", "by", "do"}: the
                                role that performs it and the skill — `by` is `human`,
                                and `do` null, where a human's decision is waited for
                   ends         where its passes end: `land`, the landing train — its
                                issues end in a PR landed on the base branch — `done`,
                                nothing more to do, or both, by different stages
                   line         the line that opens an issue into it. Give it a title
                                and a file holding the body
    keep_off     the labels that keep an issue from being worked as one of a workflow,
                 {"epic_labels", "escalate_label", "lock_label"}: an issue carrying an
                 epic label is never dispatched; the escalate label is the fleet's to
                 put on, when it hands an issue to a human; and an open issue carrying
                 the lock label is a fleet lock, which stops all other work
                 (`afkconvoy lock --help`)
    intake       {"open", "limit"}: the open issues workers took in, against the repo's
                 `intake_limit`. An issue a human opens with a flow label is outside
                 both: nothing refuses it
    created      the flow labels this run created on the repo; empty when it had them
                 all

  In an unbound repo, which has no workflow:

  {"team": null, "ready_label", "line", "keep_off", "created"}

    ready_label  the label an issue is worked under
    line         the line that opens an issue carrying it
    keep_off     as above; the escalate label is the config's
    created      the ready label, when this run created it; else empty

  Errors, as {"error": …} with a non-zero exit: the team has a fault — {"error",
  "faults"}, as `check` answers it; the team's repo cannot be read; the config cannot
  be read; "is not in a git checkout"; GitHub refused to list or create a label.

WHAT TRIPS YOU UP

  - `gh issue create --label` refuses a label the repo lacks, and nothing but this
    command creates a flow label ahead of the first issue. Run it before the line.
  - An issue follows one workflow: put one flow label on it. With several it follows
    none, and no stage of any is performed on it.
  - The flow label is what hands the issue over. Leave it off an issue that is not
    ready to be worked, and put it on later: `gh issue edit <n> --add-label <label>`.
  - A workflow whose `first` is `by: human` starts by waiting for a human: the fleet
    does nothing on its issue until one declares a verdict (`afkconvoy verdict --help`).
  - It answers the team as pushed to its default branch. A workflow added in a checkout
    of the team is not answered, and its label not created, until it is pushed.
  - A label of a workflow the team no longer has is left on the repo: this command
    creates labels and removes none.
