  A team is a directory — a whole repo, or a subdirectory of one — that holds:

      team.md                 the team file
      CLAUDE.md               the team rules: what every worker of the team works under
      workflows/<name>.md     one file per workflow; its flow label is `flow:<name>`
      patrols/<name>.md       one file per patrol; a repo runs the ones its `patrols` names
      precedents.md           the precedents: one line per ruling a human accepted

  and of each definition file — the team file, a workflow's, a patrol's — only the first
  ```yaml block is read — and, of a workflow's, the prose
  above it: what the workflow is for and what an issue of it holds, which
  `afkconvoy flows` answers to whoever opens one. The team file:

      escalate_label: ready-for-human    # default
      roles:
        <short name>: <its directory>    # owner/repo, owner/repo/path or ./path: below
      precedents: { by: <role>, do: <skill>, max_open: 10 }   # optional; see below

  A workflow file:

      max_rework: 3                      # default
      max_consecutive_rework: 2          # default
      stages:
        - name: <unique; not land, done or human>
          by: <role> | human
          do: <skill>                    # required unless by: human
          harness: claude-code           # optional; see below
          model: <model>                 # optional; its harness's own name for it
          writes: false                  # optional; default true
          escalate: { to: <role>, do: <skill> }                  # optional
          on: { pass: <stage> | land | done, reject: <earlier stage> }   # reject optional
      land: { by: <role>, do: <skill> }  # required exactly when a pass leads to land

  A patrol file — its name words of lowercase letters and digits, each starting with a
  letter, joined by `-`, 40 characters at most:

      by: <role>
      do: <skill>
      every: 6h                          # required: a whole number from 1 up, then m, h or d
      harness: claude-code               # optional; see below
      model: <model>                     # optional; its harness's own name for it
      max_open: 5                        # required: it is skipped once this many issues
                                         # it opened are open

  `harness` names the harness the stage's worker, or the patrol's, is a session of. It
  is a key of a stage a role performs and of a patrol — wherever `model` is one — and
  nowhere else: a consult, a landing and the proposal of a precedent run on the
  default. One that names none takes the default too, which is the `harness` of the
  repo's config, and claude-code where that names none. The harnesses are claude-code,
  Claude Code, and pi.

  `precedents` names who proposes a human's ruling as a precedent: the fleet starts one
  worker in that role, with that skill, for each ruling a human gives an escalated issue
  (`afkconvoy rule`), to open a PR on the team's repo that appends one entry to
  `precedents.md`. `max_open` is required: no proposal is started while that many are
  open there. A team without the key has no precedents proposed (`afkconvoy tick --help`).

  A role is a directory too — a whole repo, or a subdirectory of one — and the team file
  names it in one of three ways:

      owner/repo                         a whole repo
      owner/repo/path                    a subdirectory of a repo: the first two segments
                                         are the repo, the rest the path from its root
      ./path                             a subdirectory of the repo the team itself is in

  A `./path` is read from the root of the team's repo, not from the team's directory: a
  team and its roles in one repo name no repo at all, and two teams of one repo name the
  same role alike. Every role is read at the head of its repo's default branch, and
  nothing names a branch or a tag. Two names may be given to one directory. A role's
  directory is not the team's and does not contain it, is not inside the team's
  `workflows/` or `patrols/`, and neither contains another role's nor is inside one. It
  holds:

      CLAUDE.md                          its rules: what a worker in it always works under
      .claude/skills/<skill>/SKILL.md    one directory per skill it can be asked to perform
      .claude/settings.json              its limits for claude-code: hooks, and the
                                         permissions it denies
      .pi/extensions/                    its limits for pi: extensions

  The rules and the skills are written once, and every harness works under them. The
  limits — what the role may never do — are written once for each harness its stages
  run on, in that harness's own form, and a role needs only those of the harnesses it
  runs on. Claude Code loads its three from the directory a worker starts in; none of
  them has a key the fleet reads. A `do` names an entry of `.claude/skills/` in the
  directory of the role beside it. A worker is given its role's directory alone, and nothing else of its
  repo: a role that is a whole repo, opened by hand, is the role a worker gets, and one
  in a subdirectory is too unless a directory above it holds a `CLAUDE.md` or a
  `.claude/`, which Claude Code loads for a session opened by hand and a worker never
  sees. A symlink in such a role that leaves its directory would point at nothing: it is
  a fault. The team's directory is given to every worker beside its role's, without the
  directories of its roles and without a `.claude/` at its top: a worker's skills and
  hooks are its role's, not its neighbours' and not the ones a repo holds for whoever
  edits it.

  The `CLAUDE.md` in the team's directory is the team rules, and it is optional. Every
  worker of the team is given it, whatever its role and whatever it was started for — a
  stage, a consult, a patrol, the proposal of a precedent, a landing — and no key turns
  it off. It has no key the fleet reads. A role two teams name works under the rules of
  the team whose stage it is in. A worker reads four kinds of text, and each is for one
  thing:

      the repo's own rules     the `CLAUDE.md` (or, for pi, `AGENTS.md`) of the repo an
                               issue is of: what that one codebase asks
      the team rules           the `CLAUDE.md` of the team's directory: how the team
                               works, in every repo bound to it
      a role's rules           the `CLAUDE.md` of the role's directory: what one kind of
                               worker does, whichever stage it is in
      the precedents           `precedents.md` of the team's directory: what a human
                               ruled before, followed instead of asking again

  The first three are loaded by the worker's harness, not copied into its brief, and
  the brief says where each of the four is. They have no order: a team's rules and a
  role's that contradict each other are a defect of the team's files, and nothing says
  which holds. A `.claude/` in the team's directory is loaded by no worker — hooks and
  skills are a role's — and `afkconvoy check` notes one.

  A role whose stages run on pi keeps the same rules and the same skills: pi reads
  `CLAUDE.md` from the directory it starts in, the fleet names `.claude/skills/` to
  it, and has it load the team rules as well. Its limits are the part written once per
  harness: pi runs no hook of `.claude/settings.json`, so what such a role may never do
  is an extension of pi's in `.pi/extensions/`, which the fleet has pi load. What a pi
  worker is started with: `afkconvoy run --help`.

  `afkconvoy check` holds a role and a team to their harnesses. A role's directory that
  holds an `AGENTS.md`, an `AGENTS.MD` or an `AGENTS.override.md` is a fault: pi loads
  the first of those in place of `CLAUDE.md`, and the role would have two sets of rules.
  A role that holds limits for one harness and none for another is right for the first
  alone: a stage, a patrol, a consult, a landing or the proposal of a precedent that
  runs such a role on the other is a fault, and a role with no limits at all is right
  for every harness. Whether a role's limits for two harnesses refuse the same things
  is not checked: that is the role's to see to.
