  A team is a directory — a whole repo, or a subdirectory of one — that holds:

      team.md                 the team file
      workflows/<name>.md     one file per workflow; its flow label is `flow:<name>`
      patrols/<name>.md       one file per patrol; a repo runs the ones its `patrols` names

  and of each file only the first ```yaml block is read — and, of a workflow's, the prose
  above it: what the workflow is for and what an issue of it holds, which
  `afkconvoy flows` answers to whoever opens one. The team file:

      escalate_label: ready-for-human    # default
      roles:
        <short name>: <its directory>    # owner/repo, owner/repo/path or ./path: below
      precedents: { by: <role>, do: <skill>, max_open: 10 }   # optional; see below

  A workflow file:

      max_rework: 3                      # default
      max_consecutive_rework: 2          # default
      stages:
        - name: <unique; not land, done or human>
          by: <role> | human
          do: <skill>                    # required unless by: human
          harness: claude-code           # optional; see below
          model: <model>                 # optional; its harness's own name for it
          writes: false                  # optional; default true
          escalate: { to: <role>, do: <skill> }                  # optional
          on: { pass: <stage> | land | done, reject: <earlier stage> }   # reject optional
      land: { by: <role>, do: <skill> }  # required exactly when a pass leads to land

  A patrol file — its name words of lowercase letters and digits, each starting with a
  letter, joined by `-`, 40 characters at most:

      by: <role>
      do: <skill>
      every: 6h                          # required: a whole number from 1 up, then m, h or d
      harness: claude-code               # optional; see below
      model: <model>                     # optional; its harness's own name for it
      max_open: 5                        # required: it is skipped once this many issues
                                         # it opened are open

  `harness` names the harness the stage's worker, or the patrol's, is a session of. It
  is a key of a stage a role performs and of a patrol — wherever `model` is one — and
  nowhere else: a consult, a landing and the proposal of a precedent run on the
  default. One that names none takes the default too, which is the `harness` of the
  repo's config, and claude-code where that names none. claude-code, Claude Code, is the
  only harness there is.

  `precedents` names who proposes a human's ruling as a precedent: the fleet starts one
  worker in that role, with that skill, for each ruling a human gives an escalated issue
  (`afkconvoy rule`), to open a PR on the team's repo that appends one entry to
  `precedents.md`. `max_open` is required: no proposal is started while that many are
  open there. A team without the key has no precedents proposed (`afkconvoy tick --help`).

  A role is a directory too — a whole repo, or a subdirectory of one — and the team file
  names it in one of three ways:

      owner/repo                         a whole repo
      owner/repo/path                    a subdirectory of a repo: the first two segments
                                         are the repo, the rest the path from its root
      ./path                             a subdirectory of the repo the team itself is in

  A `./path` is read from the root of the team's repo, not from the team's directory: a
  team and its roles in one repo name no repo at all, and two teams of one repo name the
  same role alike. Every role is read at the head of its repo's default branch, and
  nothing names a branch or a tag. Two names may be given to one directory. A role's
  directory is not the team's and does not contain it, is not inside the team's
  `workflows/` or `patrols/`, and neither contains another role's nor is inside one. It
  holds:

      CLAUDE.md                          its rules: what a worker in it always works under
      .claude/skills/<skill>/SKILL.md    one directory per skill it can be asked to perform
      .claude/settings.json              its hooks: the limits it cannot cross

  Claude Code loads all three from the directory a worker starts in; none of them has a
  key the fleet reads. A `do` names an entry of `.claude/skills/` in the directory of the
  role beside it. A worker is given its role's directory alone, and nothing else of its
  repo: a role that is a whole repo, opened by hand, is the role a worker gets, and one
  in a subdirectory is too unless a directory above it holds a `CLAUDE.md` or a
  `.claude/`, which Claude Code loads for a session opened by hand and a worker never
  sees. A symlink in such a role that leaves its directory would point at nothing: it is
  a fault. The team's directory is given to every worker beside its role's, without the
  directories of its roles and without a `CLAUDE.md` and a `.claude/` at its top: a
  worker's rules and skills are its role's, not its neighbours' and not the ones a repo
  holds for whoever edits it.
