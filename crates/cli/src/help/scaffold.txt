WHEN TO RUN IT

  To start a team from files `check` accepts as they are, instead of from an empty repo.
  A team and its roles, in one repo created on GitHub:

      afkconvoy scaffold team hospital --role fellow --role attending --repo acme/hospital
      afkconvoy check --team acme/hospital

  And to add a role to a team that is there, in a checkout of its repo:

      afkconvoy scaffold role roles/reviewer

  From there on a team is designed by editing its files and running `check`.

WHO RUNS IT

  The operator, or whoever designs the team: anywhere. It reads no config.

WHAT IT READS AND WRITES

  It writes in the directory named, which must not be there yet or be empty: nothing is
  ever overwritten.

  `scaffold team <dir> --role <name>…` writes the team's files, and each role's under
  `roles/<name>/`:

      team.md                  the team file, naming each role as `./roles/<name>`
      CLAUDE.md                the team rules: a heading, and what belongs there and what
                               belongs in a repo's own rules or a role's
      workflows/feature.md     one workflow, `feature`: one stage the first role performs
                               as its skill `implement`, then the landing train
      roles/<name>/            that role's skeleton, as `scaffold role` writes it

  `--role` is given once for each role, and at least once. `--role <name>` is a role
  written here. `--role <name>=<owner/repo>` or `<name>=<owner/repo/path>` is one that
  is elsewhere — a role several teams share, in a repo of its own: `team.md` names it as
  given and nothing is written for it. The two forms mix. The example workflow is
  performed by the first role given; one that is elsewhere must hold a skill `implement`.

  `scaffold role <dir>` writes a role's three kinds of file, and takes no `--role`:

      CLAUDE.md                            rules to replace with the role's own
      .claude/skills/implement/SKILL.md    one example skill, `implement`
      .claude/settings.json                hooks: none yet

  The role's name is the directory's. Run in a checkout, it writes there and creates
  nothing on GitHub: commit and push it with the team.

  With `--repo <owner/repo>` it then makes the directory a git repo, commits the
  skeleton, and creates that repo on GitHub with the commit pushed to it:
  `gh repo create <owner/repo> --private --source . --push`, run there. `--public`
  creates it public instead. Without `--repo` it runs no `gh`, and of `git` only the
  question of which checkout the directory is in: a role's path in `team.md` is written
  from the root of the team's repo, so a team written in a subdirectory of a checkout
  names its roles from that checkout's root.

  A skill is added to a role afterwards with the skills installer, run in the role's
  directory and committed: this command installs none.

WHAT IT ANSWERS

  {"scaffolded", "dir", "files", "repo", "team_line"} — "team" or "role"; the directory
  written in, as an absolute path; the files written, as paths in it; the repo created,
  null without `--repo`; and, of a role, the line to add under `roles` in `team.md`:

      scaffold role roles/reviewer          "team_line": "reviewer: ./roles/reviewer"
      scaffold role dev --repo acme/dev     "team_line": "dev: acme/dev"

  `team_line` is null of a team, and of a role nothing says the repo of: one written
  outside any checkout with no `--repo`, or as the root of one.

  Errors, as {"error": …} with a non-zero exit: the directory is not empty; a team with
  no `--role`, or one name given twice; a role with a `--role`; a `--role` that is
  neither <name> nor <name>=<owner/repo[/path]>; a file that cannot be written; and,
  with `--repo`, a `git` or `gh` call that failed — the error says the skeleton is
  written and its repo is not created.

WHAT TRIPS YOU UP

  - `check` reads every role from GitHub: a team's skeleton passes it once it is pushed
    — `--repo` does that — and not before.
  - `check --dir <dir>` alone refuses a role named `./path`: a directory says no repo.
    Say the team's beside it — `check --dir <dir> --team <owner/repo>` — as the
    skeleton's own files do.
  - A role that is elsewhere must be on GitHub, with its skill on its default branch,
    before the team that names it passes `check`.
  - After a failed `--repo` the directory is no longer empty. Create the repo yourself
    from it with the `gh` line above; do not run this again on it.
  - `--repo` commits as whoever git is set up for on this host, and creates the repo as
    whoever `gh` is logged in as. Every host of a fleet must be able to read it.
