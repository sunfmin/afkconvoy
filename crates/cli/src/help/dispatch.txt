WHEN TO RUN IT

  To start a worker on one issue by hand. A tick does this on its own for every frontier
  issue it has a free slot for, and for every claim of its own left without a worker. Do
  it yourself when a plan shows an issue the fleet is not starting, or — with `--start
  fresh` — to throw away an attempt that went wrong and have the issue worked again.
  Run `recovery` first: it shows what this would continue from.

WHO RUNS IT

  The operator, in a checkout of the repo, on the host the worker is to run on.

WHAT IT READS AND WRITES

  It claims the issue for `--instance` unless that instance holds it already, looks at
  what survives of an earlier attempt, has orca put a worktree there, records the
  worktree's branch in a comment on the issue, writes the worker's brief into the
  worktree, starts the worker launch command in it, and hands the worker its prompt.

  In a bound repo the issue's flow label names its workflow, and the worker performs
  that workflow's first stage in the stage's role. The team's repo and each role's are
  asked for the commit at their head; one the fleet has no copy of yet is cloned and
  kept, read-only, under the user's cache directory (afkconvoy/copies/<owner>/<repo>/
  <commit>). The terminal is opened on the worktree as ever, and the line it runs
  changes to the role's copy, puts the stage's facts in the environment (AFKCONVOY_ISSUE,
  _FLOW, _STAGE, _ROLE, _SKILL, _WRITES, _ROLE_COMMIT, _TEAM_COMMIT), and starts the
  worker launch command with the worktree and the team's copy added as directories, the
  user's own settings left out, and the stage's model when it names one.

WHAT IT ANSWERS

  {"issue", "started": true, "claim", "tier", "action", "prompt", "reason", "worktree",
   "branch", "terminal"}

    claim      won (claimed now) or held (the instance's already)
    tier, action
               1 reuse_worktree — the worktree is still on this host; 2 recreate_at_tip
               — a new worktree at the issue's pushed branch; 3 dispatch_fresh — a new
               worktree at the base branch
    prompt     the brief the worker got: fresh, continue, or join (its PR is open: only
               the join is left) — in a bound repo, stage
    stage      in a bound repo: {flow, name, role, skill, writes, model, role_commit,
               role_dir, team_commit, team_dir} — the stage the worker performs, and the
               copies and commits fixed for it
    reason     why that tier, in words
    discarded  with `--start fresh`: {closed_prs, deleted_branches, removed_worktree}

  {"issue", "started": false, "claim": "lost", "owner"} — another instance holds the
  claim. Nothing was started.

  Errors: the issue is closed; in a bound repo, the issue carries no flow label, more
  than one, or one that names no workflow of the team, or the team does not load (the
  error carries its `faults`) — none of which claims the issue; the worker launch
  command resolves to nothing; orca
  fails, or the worker is not ready in time. After a failed step the claim is still
  held: the instance's next tick finds a claim with no worker and continues it.

WHAT TRIPS YOU UP

  - `--instance` is required, and it is the instance that holds the claim afterwards.
    Give it the id of the fleet that is to look after the worker.
  - `--start fresh` discards the previous attempt: it closes the issue's open PRs,
    deletes its branches on the remote and removes its worktree, unpushed work included.
  - It checks that the issue is open, and nothing else of the frontier: an issue without
    the ready label, with an open blocker, or past the concurrency is started all the
    same.
  - It does not ask after a worker already there. On a claim whose worker is at work it
    starts another in the same worktree.
