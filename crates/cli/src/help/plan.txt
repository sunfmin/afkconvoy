WHEN TO RUN IT

  Before `run`, to see what the fleet would start on; and beside a running fleet, to see
  where every claim stands and why an issue is not on the frontier.

WHO RUNS IT

  The operator, in a checkout of the repo.

WHAT IT READS AND WRITES

  It makes the startup probe — which checks, as a start does, the worker launch command
  a `run` started now would give every harness the fleet could be asked for
  (`afkconvoy run --help`) — then the rebuild: the open issues and PRs on GitHub, the
  claims and heartbeats on the remote, and the landing train. It changes nothing on
  GitHub. On the remote it pushes its startup probe and deletes it again, together with
  what the probe sweeps: a probe an earlier start left behind, and recorded gate runs
  too old for a landing to believe.

  WHEN IT PROBES. Not every time: a startup probe that passed on this host in the last
  hour stands, and `plan` then makes none — it says so on stderr, repeats that probe's
  warnings, and pushes nothing. It probes when no probe stands: none passed on this
  host within the hour — `run` makes one at every start, `tick` and `plan` when they
  find none — or the config's `base_branch` or `team` changed since, or the remote's
  URL did, or the note of where the remote keeps the fleet's refs. The probe is noted
  in the repo's git dir (`convoy-probe`); delete that file to have the next `plan`
  probe.

  The rebuild asks GitHub twice, side by side with one listing of the remote, however
  many issues are open: one query for the open issues with their comments (an issue
  with more than a hundred comments is asked about once more), one for the open PRs.
  It asks once more — for the issues that carry the label `slow-gate` — only while the
  recorded gate runs of the base branch's landings say the gate is slow.

WHAT IT ANSWERS

  {"frontier", "excluded", "waiting_on_human", "mine", "peer_live", "stale",
   "stale_closed", "free_slots", "now", "locks"} — and in a bound repo "intake", "patrols" where it names some, and
   "proposals" while a ruling is proposed as a precedent or waits to be; and "slow_gate"
   while the gate is slow

    frontier       the issues a tick would dispatch, lowest number first: {number, title}
                   — in a bound repo with the stage each is at: {number, title, stage},
                   those a stage has already declared on ahead of those never started;
                   an issue whose stage's `escalate` waits for its consult is here
                   too, at that stage; the stage is `land` once the last one passed to the landing train
                   and the issue's PR waits for a worker to join it
    excluded       every other open issue, with why: {number, title, reason}. An
                   escalated issue says so — "escalated: waits for a ruling" — and
                   not that it lacks the label its escalation took off
    waiting_on_human
                   every open issue nobody holds that waits for a human, lowest number
                   first: {issue, title, why, since, answer} — why in a few words,
                   since when in epoch seconds where GitHub said, and the line that
                   answers it, to run as it is but for what stands between < and >.
                   They are: an escalated issue, one whose records call for a human,
                   one at a stage that is a human's, one whose workflow ended and
                   that is still open, and the report of a patrol's failed run
    escalating     in a bound repo, when there are any: the unclaimed issues a tick
                   hands to a human, with why: {number, title, reason}
    mine           the claims of `--instance`: {number, title, status, pr, declared} —
                   `declared` is true while a verdict declared under the claim waits to
                   be acted on: the claim takes no slot meanwhile. In a bound
                   repo with `due`, the stage a worker is to be started on once the
                   claim's stage has declared, where a role performs one. status is
                   no_pr, joining, joined, landed or closed — in a bound repo at_stage,
                   whatever PR is open, until a landing worker holds the claim: then
                   joining, joined, landed or closed, as in an unbound repo
    peer_live      other instances' claims within the lease — never touched
    stale          other instances' claims past the lease, on open issues — a tick
                   takes them
    stale_closed   the same on closed issues — a tick deletes them
                   (each of the three: {number, instance, sha})
    free_slots     how many more claims the instance may take
    now            the time the plan was made at, in epoch seconds
    locks          the fleet locks standing: the open issues that carry the lock label,
                   lowest number first — none: []. While there is one, the frontier
                   holds lock issues only, and every issue a tick would otherwise
                   dispatch or hand to a human is under `excluded` with the reason
                   "a fleet lock stands (#n)"
    intake         in a bound repo: {"open", "limit"} — the open issues taken in by
                   workers, counted from their intake records, against the repo's
                   `intake_limit`. With `open` at `limit`, `afkconvoy intake` refuses.
                   An issue a human labelled is not among them

    patrols        in a bound repo that names patrols: each, in the order the config
                   names them: {name, standing, every, last_run, open, max_open} —
                   `every` in seconds, `last_run` when its last recorded run started
                   (null: it never ran), `open` the open issues it opened. standing
                   says what a tick does about it:
                     due           its interval has passed: a tick runs it
                     not_due       its interval has not passed since `last_run`
                     locked        a fleet lock stands: no patrol runs
                     full          `open` has reached `max_open`
                     failed        its last run failed, and the issue that reports it —
                                   `failure`, in this case only — is still open
                     running       a run of `--instance` is still going
                     peer_running  a live peer's run is still going
                     stale_run     the run is claimed by a peer presumed dead: a tick
                                   deletes that claim
    proposals      in a bound repo whose team names who proposes precedents: each
                   ruling of a human that is being proposed, or is still to be:
                   {issue, comment, standing} — the issue ruled on and the id of the
                   comment that is the ruling. standing says what a tick does about it:
                     due           a tick starts its worker, once the frontier is served
                     full          the open proposals on the team's repo have reached
                                   the team's `max_open`
                     locked        a fleet lock stands: nothing is proposed
                     running       its worker, started by `--instance`, may still be at it
                     peer_running  a live peer started its worker
                     stale_run     it is claimed by a peer presumed dead: a tick ends it
    slow_gate      while the gate is slow: {gate_seconds, host, runs, issue}. On `host`,
                   the last 5 landings on the base branch that have a recorded run of
                   the config's `gate_command` with a time all took more than 80% of
                   the gate limit, `gate_seconds`. runs are those 5, newest first:
                   {commit, seconds}. issue is the open issue that says so — the
                   lowest open one carrying the label `slow-gate` — or null: a tick
                   opens one (`afkconvoy tick --help`)

  The probe's warnings go to stderr. Errors: a command the fleet needs is missing or
  logged out, or orca is not running or does not know this checkout (the error names
  each, with the line to run; `claude` is among them when
  no custom provider is set, as `run` would then start its workers with it); the repo
  fails the startup probe (the remote has no base branch, its protection refuses the
  fleet's push, or the remote takes none of the fleet's refs); the config cannot be
  read; GitHub or the remote cannot be read.

WHAT TRIPS YOU UP

  - Without `--instance` nobody's claims are its own: `mine` is empty, a running
    fleet's claims show under `peer_live`, and `free_slots` is the whole concurrency.
    To see a running fleet as it sees itself, pass its instance id — `takeover --list`
    shows every id the remote remembers.
  - A lock that stands is not thereby worked. A lock issue is on the frontier only when
    it would be without the lock: with the ready label in an unbound repo, a flow label
    in a bound one, no epic label, no open blocker, no claim. `excluded` says which
    of these keeps it off — and the lock stands until the issue is closed.
  - `frontier` is what the rebuild read, and `plan` reads nothing more. An issue that
    gains an open blocker after it is still listed; a tick reads each issue's blockers
    once more just before it claims it, and skips the issue then.
  - A patrol is due or it is not: one that missed ten intervals runs once. And a run
    still going takes one slot of `concurrency`, like a claim on an issue.
  - With a lock standing, `free_slots` counts as free the slot of every claim of
    `--instance` the lock leaves alone: a lock issue does not wait for them.
  - `free_slots` counts as free the slot of every claim of `--instance` that is
    `declared`: `mine` may hold more claims than the concurrency, and the frontier
    does not wait out the grace period of a worker that already declared.
  - "Changes nothing" is about fleet state. When it probes it still pushes to the
    remote, and deletes there: it needs push access, and it is not a read-only command.
  - A slow gate is read off the recorded gate runs the remote still has: a record is
    swept a day after its run, a landing with no record or with a record that states
    no time is passed over, and 5 landings spread over hosts none of which has 5 say
    nothing. After an issue for a slow gate closed, only the landings made since count.
  - A probe that stands is trusted, not checked: a command uninstalled or logged out
    since, or a rule the remote gained, shows as the error of whatever runs into it —
    or, for the ref layout, not until the next probe. `run` probes at every start.
