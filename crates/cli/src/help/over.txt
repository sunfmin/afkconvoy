WHEN TO RUN IT

  Once, as the last command of a worker that is on no issue: a patrol's, when it has
  nothing more to open, and a proposal's, when its PR is open or there is nothing to
  propose. The worker's brief ends with the exact line, the run named in it.

WHO RUNS IT

  A patrol's worker or a proposal's, in its own worktree: the checkout it was started
  in. Never a worker on an issue: its stage ends with a verdict (`afkconvoy verdict
  --help`).

WHAT IT READS AND WRITES

  It reads the claim on the run off the remote and pushes one record that names it — a
  ref of the fleet's, `over/<run>` — then wakes the `run` of this host (`afkconvoy wake
  --help`). The next tick finds the run declared over and ends it at once, as it would
  one whose worker is gone (`end_patrol`, `end_proposal`: `afkconvoy tick --help`): a
  patrol's checkout is still checked for a commit and a PR, a proposal's PR is still
  held against its ruling. The slot the run held is free from that tick on.

WHAT IT ANSWERS

  {"over": true, "run", "ref", "woke"} — the record is on the remote; `woke` is whether a
  `run` on this host was told.

  Errors: no run is claimed under that name — it was ended already, or never started;
  the name is an issue's number; the worker is on an issue (AFKCONVOY_ISSUE is in the
  environment); the remote cannot be read or does not take the push.

WHAT TRIPS YOU UP

  - It ends nothing itself: the fleet ends the run, at its next tick. A worker that goes
    on working after it is cut short.
  - A worker that never runs it loses nothing but time: the fleet ends the run once the
    worker is gone, or has been stopped for the grace period — five minutes in which
    the run holds a slot of `concurrency` no issue can be worked in.
  - The record names the claim it was read from: left behind, it says nothing of the
    next run of the same patrol.
