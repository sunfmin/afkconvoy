WHEN TO RUN IT

  `land --issue <n>`: once the PR is open and its gate run is green and on record, to
  join the PR to the landing train. A worker's prompt names the exact command.
  `land --train`: when the train's worker is told a PR joined, and again after each
  answer that says so, until the answer is `idle`.

WHO RUNS IT

  `--issue`: the worker that wrote the PR, in its own worktree — in a bound repo, the
  worker in the landing role of the issue's workflow, in the issue's worktree.
  `--train`: the train worker, in the train's worktree — never anybody else, anywhere
  else.

WHAT IT READS AND WRITES

  `--issue` reads the open issues, the open PRs and the train. With a fleet lock
  standing it joins the PR of a lock issue only, and for any other changes nothing.
  Otherwise it pushes this branch when it is ahead of the remote's, then pushes one
  merge commit — the PR's head joined onto the train's tip — as the train's new tip.
  No gate runs, and nothing on GitHub changes. A PR that conflicts with the train gets
  the train's tip merged into this worktree, left in progress.

  `--train` puts this worktree on the train's tip, merges the base branch in when it
  moved, pushes that as the train's tip, and gates it — by the run on record for that
  tree, which it leaves as it is, else by a run made now, for no longer than the gate
  limit: the config's `gate_seconds` (default 3600), as for `afkconvoy gate`. That run
  is put on record with the seconds it took and the host (`--host`, else this
  machine's name). Green: it pushes the commit to the base branch as a
  fast-forward, closes the issue of every PR that landed, and deletes those PRs'
  branches once GitHub shows them merged. Red: it comments the failure on every PR on
  the train, and lands nothing. Either way it then measures this worktree: what git
  ignores in it, and the files git tracks; the first run here notes what it built.

WHAT IT ANSWERS

  `--issue`: {"issue", "pr", "outcome", "detail", …}

    joined    the PR is on the train — stop. With "head", "commit" (the join commit) and
              "again": true when it was there already
    merged    the base branch already holds the PR's head — stop. With "head"
    conflict  with "files" and "worktree": resolve every file, commit the merge, run the
              gate again, then this again
    locked    a fleet lock stands, and this issue is not one: nothing joined and nothing
              was pushed — stop, and run this again when told to carry on. With "locks",
              the lock issues

  `--train`: {"train", "base", "outcome", "detail", …}

    idle          nothing is on the train
    conflict      with "files" and "worktree": resolve, commit the merge, run it again
    gate_red      with "commit", "prs" and "gate" {status, exit_code, timed_out, seconds,
                  command, excerpt}: fix the train with one more commit here, run it again.
                  A run ended at the gate limit has exit_code 124 and timed_out
                  true, and "detail" says so, and what the limit is
    target_moved  the base branch moved while the gate ran; nothing landed — run it again
    landed        with "commit", "prs", "gate" {status, source, command, at, seconds,
                  host}, "landed" [{issue, pr, commit}], "unmerged" (PRs GitHub still
                  shows open) and "more": true when the train grew meanwhile. "seconds"
                  and "host" are how long the gate command ran and where, as the run
                  that answered says — the one on record ("source": "recorded") or the
                  one made now ("run"); a run recorded with no time has neither

    gate_red and landed also say, in bytes, what this worktree holds once it is gated:

    built   everything git ignores here — what gate runs built, every older artifact a
            build tool keeps beside the newest included
    fresh   what this worktree held after the first gate run since it was cut: its
            fresh build. Noted once, in this worktree's own git dir, so a worktree cut
            again notes it anew; never noted when the worktree held ignored files before
            that run, and absent while none is on record
    source  the files git tracks, for reference only: how many times this a build comes
            to differs from repo to repo, so it decides nothing

    This worktree is kept with what its gate runs built, landing after landing, until
    it has outgrown its fresh build: built more than 3 times fresh and more than 1 GiB
    — more than 1 GiB alone while no fresh is on record. Then the next tick that finds
    the train idle — nothing on it, and its worker not at work — removes the worktree
    and cuts it again at the base branch's tip, its notes with it; the run log says so,
    with built and fresh. The next gate run here builds from nothing, and is slower.

  Errors: no open PR closes the issue; tracked files have uncommitted changes; the
  remote has no such branch; the train moved under the command too many times ("run this
  again"); for `--train`, untracked files in the worktree ("is not the commit that would
  land").

WHAT TRIPS YOU UP

  - `--train` moves the branch checked out here onto the train's tip, with a hard reset.
    Run in a checkout of your own it takes that checkout's branch with it.
  - Joined is not landed. `--issue` ends at `joined`; the train worker gates and lands.
  - A `gate_red` may be the base branch's, not the train's: the train worker gates
    `origin/<base>` alone, in a clean checkout, and red the same way is a defect it
    records — on the open issue that already does, or on one it opens. In an unbound
    repo that one carries the ready label; in a bound repo, where only a flow label
    dispatches, it takes it in with `afkconvoy intake --train`: to the team's first
    workflow, unless another fits it clearly better. Then it goes on with the train.
  - `--issue` runs no gate. It joins whatever is committed: run `gate --train` first.
  - `--merged-timeout` and `--host` are read by `--train` only. How long the gate may
    run is no flag: it is `gate_seconds` in the config (`afkconvoy config --help`).
