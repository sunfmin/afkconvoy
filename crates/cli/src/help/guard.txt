WHEN TO RUN IT

  Never by hand. It is the guard: the check made before each thing a worker of a bound
  repo does, refusing what no worker may do and what its stage may not. Read this to
  learn what a worker is refused, or why one was.

WHO RUNS IT

  Claude Code, as a hook: the fleet adds it to every worker of a bound repo as it
  starts it, whatever the role's repo holds, and Claude Code runs it before each tool
  call the worker makes. A call it refuses is not made.

  Under pi, which has no hooks, the extension the fleet starts every worker with runs
  it before each tool call, and describes the call in Claude Code's words: pi's `bash`
  is judged as `Bash`.

  A role's own limits are hooks in the role's repo. They load because the worker starts
  there, run beside this one, and refuse in the same way. Under pi the same extension
  runs the role's `PreToolUse` hooks.

WHAT IT READS AND WRITES

  It writes nothing. It reads two things:

  Standard input: one tool call, as Claude Code describes it to a `PreToolUse` hook —
  a JSON object with `tool_name` and `tool_input`. Only a `Bash` call is judged, by the
  words of each simple command of its `tool_input.command`.

  The environment: the facts of the worker's stage, which the fleet put there when it
  started the worker — AFKCONVOY_STAGE, AFKCONVOY_WRITES, AFKCONVOY_CONSULT,
  AFKCONVOY_BASE_BRANCH, AFKCONVOY_ESCALATE_LABEL, AFKCONVOY_LOCK_LABEL.

  Refused for every worker:
    - adding or removing a flow label, a `stage:` label, the escalate label or the lock
      label (`gh issue edit --add-label`, `--remove-label`, `gh issue create --label`,
      and any write of an issue's labels through `gh api`)
    - writing a stage record by hand: only `afkconvoy verdict` writes one
    - writing an intake record by hand: only `afkconvoy intake` writes one, and it is
      what puts a flow label on for a worker
    - merging a PR (`gh pr merge`, or the merge endpoint through `gh api`)
    - pushing the base branch (`git push` with a refspec that lands on it, `--all`,
      `--mirror`)

  Refused besides in a stage its workflow marks `writes: false`, for every consult, and
  for a patrol's worker (AFKCONVOY_PATROL, in place of a stage's facts):
    - committing and pushing (`git commit`, `merge`, `cherry-pick`, `revert`, `am`,
      `push`)

WHAT IT ANSWERS

  Unlike every other command, no JSON: it answers Claude Code the way a hook does.

    exit 0, nothing printed   the call is allowed
    exit 2, a line on stderr  the call is refused; the line is the reason, and Claude
                              Code shows it to the worker

  A call it cannot read, or an environment that lacks one of the stage's facts, is
  refused with the reason: nothing is allowed unread.

WHAT TRIPS YOU UP

  - It recognises commands. The same act wrapped in a script, hidden in a variable or
    in a substitution inside quotes gets past it: it stops a worker that errs, not one
    that means to get by.
  - What it misses is checked after the stage: a commit left on the branch by a stage
    marked `writes: false`, or by a consult, is a failure, and the issue escalates; a
    commit or a PR a patrol left is a failed run, reported to a human — see
    `afkconvoy tick --help`.
  - An unbound repo's workers have no guard: their worker launch command is opaque.
