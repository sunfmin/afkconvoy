WHEN TO RUN IT

  When something looks wrong, and before anything else: a fleet that seems stuck, an
  issue nobody works, a worker that sits there — or when you are asked "is it working?".
  Run it before you file a bug, too, and put its answer in the report. It is one command
  for what `scan`, `takeover --list`, `plan`, `show` and orca each say a part of, and it
  is the only one that says what is wrong.

WHO RUNS IT

  The operator, in a checkout of the repo, on the host the fleet runs on. No `--instance`
  is needed: it finds the fleet instance of this host's `run` itself.

WHAT IT READS AND WRITES

  It reads this host (the commands the fleet needs, in a login shell; orca), the log
  this host's `run` keeps of its ticks, the open issues, PRs and stage records on
  GitHub, the claims, heartbeats and recorded gate runs on the remote, and orca after
  the worker of each claim. It writes nothing on GitHub and nothing on the remote, and
  makes no startup probe: it is safe beside a live fleet, as often as you like. It fixes
  nothing either: each finding names the command that does.

WHAT IT ANSWERS

  {"host", "fleet", "claims", "issues", "waiting_on_human", "findings"}

    host      what this host has of what the fleet needs:
                tools            each command needed — a harness only where a worker
                                 launch command the fleet could be asked for runs it by
                                 name: {name, state} — state is ready,
                                 missing or logged_out; of orca also not_running,
                                 knows_no_checkout (the checkout worktrees are cut
                                 from was never added to it) or unasked
                worker_commands  one for each harness the fleet could be asked for:
                                 {harness, called_for_by, command, from,
                                 starts_a_worker, takes_role_flags} — called_for_by is
                                 the repo's default, and each stage and each patrol the
                                 repo runs that names the harness; from is `run`, when
                                 this host's `run` logged the first word of what it
                                 started that harness with (all it logs of it), else
                                 `default`: what a `run` started now would use. In an
                                 unbound repo it is the one command, of no harness:
                                 harness is null and called_for_by empty. A harness is
                                 left out on a custom provider with no `run` to say
                admission        whether a tick would start a new worker on this host
                                 now, the thresholds in force and what the host reads:
                                 as `plan` answers it (`afkconvoy plan --help`), or
                                 {error} where a share the host says is wrong. A tick
                                 that admission held back is no "started no worker"
                                 finding
                exclusive        the host's queue of `afkconvoy exclusive`, whatever
                                 its repo: {running, waiting} — running is the command
                                 that runs alone now, null with none; waiting, those
                                 that wait their turn, next first. Each is {command,
                                 dir, issue, pid, asked, ran}: the worktree it was run
                                 in, the issue of its worker, and when it asked and
                                 began to run, in epoch seconds. {error} when the
                                 queue cannot be read
    fleet     the `run` of this host for this repo:
                alive            whether one is running now
                instance, host   its fleet instance id: the one its log names, else the
                                 one the claims stamped with this host name; null when
                                 this host never ran one
                heartbeat_age    seconds since its heartbeat; null: it has none
                heartbeats       {found, live}: how many heartbeats the remote has,
                                 whoever stamped them, and the instance ids of those
                                 within the lease. A `run` told to stop removes its
                                 own, and a start removes the dead ones that hold
                                 nothing: more than one found and not live is fleets
                                 nobody started again
                log              the file its ticks are logged in, or "no log": no `run`
                                 of this version ran here
                last_tick        {count, ended, next_due, line, did, error}: when its
                                 last tick ended and the next is due, in epoch seconds,
                                 the line `run` printed, and what `tick` answers as `did`;
                                 error, when the tick failed whole. null with no log
                failed_steps     the last ten failures, newest first: {tick, ended,
                                 do, issue, patrol, error, count}. One cause that
                                 stopped several steps of a tick is one failure: count
                                 is how many, and do, issue and patrol the first's
                host_sleep       {checked, slept, kept_awake_by}: its last check for
                                 host sleep — when it ended, whether it put the host
                                 to sleep, and else what kept the host awake, each in
                                 words. null: it made none, being told
                                 `--no-host-sleep` or never idle ten minutes
                events           the last twenty events that reached a `run` of this
                                 host, newest first, whichever instance: {at, event,
                                 cause, instance} — event being wake (between ticks,
                                 or during one), start, stop (told to, by SIGTERM or
                                 SIGINT), host_sleep or host_wake; cause says what
                                 caused it, in words. [] with no log
    claims    each claim of that instance: {issue, title, status, pr, stage, role,
              held_for, worker, worktree, gate} — status as `plan` gives it; stage and
              role in a bound repo; held_for in seconds; worker is {state, quiet}, state
              being busy, stopped or gone, and null when orca could not say; gate is
              {green_at} when a green gate run is on record for the tree the worktree
              is at, else null
    issues    as `plan` answers them: {frontier, excluded, escalating, locks, free_slots,
              patrols} — what a worker can be started on, what waits and why, and what
              is being handed to a human and why. null when they could not be read
    waiting_on_human
              as `plan` answers it, and as the panel lists it under "With a human":
              every open issue nobody holds that waits for a human — escalated, at
              a stage that is a human's, past the end of its workflow and still
              open, or reporting a patrol's failed run — each as {issue, title, why,
              since, answer}: `answer` is the line that answers it. null when the
              issues could not be read
    findings  what is wrong, most severe first — none: []. Each is {severity, what,
              evidence, fix, see}:
                severity   critical  the fleet does not work until it is fixed
                           warning   one issue or one patrol is held up, or about to be
                           info      nothing is held up: said so that a surprise is explained
                what       the fault, in a sentence
                evidence   what was read that says so
                fix        one command line to run as it is — or, for a fault in a
                           team's or a role's file, or a key the repo's config
                           leaves out, `<file>: <key>` to edit
                see        the command that prints the help topic explaining it:
                           `afkconvoy help humans` where what it reports waits for
                           a human, else `afkconvoy help troubleshooting`, which
                           has a row for each finding

  It exits 0 with no critical finding, and non-zero with one — printing the same
  object, not {"error"} — so that a script can gate on it. Errors: "is not in a git
  checkout". Whatever else cannot be read is itself a finding.

  The findings: a command the fleet needs is missing or logged out; orca cannot be
  asked, or does not know the checkout; the worker launch command of a harness the
  fleet could be asked for cannot start a worker — said with the harness and what
  calls for it; no `run` is alive and claims are held; the same step failed in each of the
  last three ticks; the team has a fault at its head; a fleet lock stands on an issue
  that cannot be worked (all critical) — a claim has no worker; a worker has been
  stopped for half an hour with its claim still at work; the frontier is not empty,
  slots are free and the last tick started nobody; a flow label names no workflow of
  the team; an issue has been at a stage longer than any before it took; an issue is
  one rework from a breaker; a patrol is failed or full; an issue has waited for a human
  for more than an hour, its `fix` being the line that answers it; the gate is slow —
  with the host, the gate limit and the 5 runs, each a commit and its seconds, as
  `afkconvoy plan` has them, and the issue open for it when there is one (all warning) — the
  role or the team a stage in flight started under has moved since; and the repo's
  config declares no gate limit, so the gate has the default's 3600 seconds before
  anything ends it: `fix` is the file and the key, `gate_seconds`; and a worktree on
  this host is kept with no claim on its issue — said with what it holds that the
  remote does not (uncommitted changes, commits only it has, or nothing), its `fix`
  the line that removes it, pushing first whatever only it holds (all info).

  Moved: the role's directory holds something else at the head of its repo than at the
  commit the stage started under — a file added, removed or changed. A new commit is
  not it: in a repo of several roles a push gives every role a new commit, and moves
  the ones whose directory it changed. The team has moved when its directory has,
  without what a worker is not given of it: the directories of its roles, and the
  .claude/ at its top. So a push that changes only a role moves no team, one that
  changes only the team's rules — the CLAUDE.md at its top, which every worker is
  given — moves the team, and one that changes a workflow moves no role. A role in a repo of its own moves with
  every push that changes a file there. The two are compared in the copies this host
  keeps (copies/ under the cache directory); where the one the stage started
  under is no longer there, a different commit is all there is to go by, and it is
  said to have moved. `evidence` gives both commits.

WHAT TRIPS YOU UP

  - A warning may be the fleet mid-step: a claim has no worker between the tick that
    took it and the one that starts its worker. Run it again after a tick before you
    act on one; a critical finding does not go away by waiting.
  - It says nothing of ticks nobody logged. A `run` logs under your cache directory
    (`afkconvoy help cache` says where it is) on the host it runs on: run `doctor` there, as the
    same user. The log is a log: nothing reads it to decide anything, and deleting it
    loses only what `doctor` could say of the ticks before.
  - It makes no startup probe, so it looks for the fleet's refs where this repo's last
    `plan`, `tick` or `run` found the remote keeps them. In a clone none ever ran in, it
    looks under refs/convoy/.
  - `fix` is the first thing to try, not a promise: read `afkconvoy <command> --help`
    of the command it names before you run it.
