WHEN TO RUN IT

  When a team has no roster yet, or the host kit has changed and its roster is to
  follow: a team's roster is drafted rather than written from nothing. Run it on a
  host whose host kit holds what the team's workers are to run (`afkconvoy kit`).

WHO RUNS IT

  Whoever designs the team, in a checkout of it: the team's working tree. The fleet
  never runs it, and never changes a team's roster.

WHAT IT READS AND WRITES

  It reads the team's files from `--dir` — this directory unless it says another —
  as `afkconvoy check --dir` does, each role from GitHub, and this host's host kit
  without the harnesses paused on it. A role named as ./path is read from the repo
  `--team` names: give it for a team whose roles are in its own repo.

  1. It sends the host kit's first — its first harness on its first model, in the
     login shell a worker gets — one prompt: every harness and model of the host
     kit in order, and each role with the work the team asks of it and what it may
     run. It waits up to nine minutes for one line for each model, saying what it
     is good at, and one for each role, saying how to cast an issue there.
  2. It drafts the team file's `roster` (`afkconvoy help roster`): an entry for
     each role, its `run` every harness and model of the host kit in the host
     kit's order, each with the `good_at` that was said of it, and the role's
     `cast`. A harness the role holds no limits for, while it holds limits for
     another, is left out of its entry and named in a comment there, so that the
     draft passes `check` as written; a role left nothing is named in a comment
     alone.
  3. It writes the draft into the team file, team.md, in place of the `roster`
     there and everything under it, or at the end of its yaml block where it has
     none. Nothing else of the file changes, and nothing is committed.

  Where the team file holds a roster, it says on stderr each line the draft would
  take out (-) and put in (+), and writes only once the human at the terminal
  confirms, or with `--yes`. With no terminal and no `--yes` it writes nothing.

WHAT IT ANSWERS

  {"path", "drafted_by", "roster", "replaces", "removed", "added", "unsaid",
  "written"}: `path` the team file, `drafted_by` the {harness, model} asked,
  `roster` the draft as written, `replaces` whether the team file held a roster,
  `removed` and `added` the lines the draft takes out and puts in, `unsaid` what
  the model said nothing of — each also a warning on stderr, to write in by hand —
  and `written` whether the team file was written. A roster the same as the draft
  is not written again.

  Errors: a team that does not load, with every fault, as `check` answers it; a
  host kit that cannot be read or holds no harness; a first harness that can be
  sent no prompt but in a worker's terminal (DSH); a model that did not answer.

WHAT TRIPS YOU UP

  - Read the draft before committing it: what a model is good at, and how to cast,
    are a model's words. Edit them, take out what a role is not to run, and order
    what is left as the team prefers — `afkconvoy check --dir` then says whether
    the team loads.
  - A team file whose roster has a fault does not load: delete the roster, and
    draft again.
  - The draft is the host kit of the host it runs on. A harness another host holds
    and this one does not is not in it.
  - Drafting sends the host kit's first a real prompt: it spends some of its login.
