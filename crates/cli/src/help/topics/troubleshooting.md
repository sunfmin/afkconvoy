Start with `afkconvoy doctor`, in the checkout the fleet runs in: it reads everything and changes nothing. Each finding has a `fix` — a line to run, or a file and key to edit — and `evidence`. Below, a row for each: the words its `what` holds, why, and what to do. Then what a start refuses with, and what neither says.

## What `doctor` finds — critical: the fleet does not work until it is fixed

- `is not installed`: A command the fleet needs is not on this host. Run `fix`: the line that installs it.
- `is not logged in`: `gh` or `claude` is logged out, as a login shell sees it. Run `fix`. Of `codex`: it has no login in ~/.codex/auth.json, the file a worker is given. One Codex keeps in a keyring is in no file: have Codex keep it in one, and run `fix`.
- `holds credentials for no provider`: A stage or a patrol runs on pi, logged in nowhere. Start `pi` and type `/login`.
- `is not running`: orca is not running, and every worker is started through it. Run `fix`.
- `cannot be asked about this checkout`: orca runs but did not say which repos it knows; `evidence` says why. Run `fix`.
- `does not know this checkout`: orca was never given the checkout worktrees are cut from. Run `fix`, once.
- `cannot start a worker`: The first word of a worker launch command resolves to nothing in a login shell, as an alias of your own shell's may. Name one that does: `afkconvoy run --help`.
- `cannot start a worker in its role`: In a bound repo the worker launch command must end in its harness, taking flags: the fleet adds what puts the worker in its role. `afkconvoy help worker-launch`.
- ``no `afkconvoy run` is alive``: The `run` of this host died holding claims. Start it here: it takes them back.
- `is broken`: This checkout's fleet instance panicked, its loop ended in an error, or its startup probe no longer passes; every other goes on, and the host runner starts it again after a backoff, when `evidence` says. Put right what `what` says, then run `fix`: a `run` starts it at once.
- `is public: its fleet instance works nothing`: GitHub says the repo this checkout's fleet reads and writes its issues in — its own, where it says no tracker — is public, so anyone can write what the fleet reads and its workers are told. Its fleet instance ends at its next check, within the hour, and every start of it is refused. Run `fix` with a private repo of yours, or make that repo private again: the next start of it works.
- `failed in each of the last`: One step fails tick after tick; `evidence` is its error, naming what refused. `fix`.
- `the team this repo names cannot be read`: The team's repo, or a role's, could not be read. `afkconvoy check` says which.
- `has a fault at its head`: A team's or a role's file is wrong on its default branch. `fix` is the file and key; `afkconvoy check` gives every fault. Push the edit: no stage starts until then.
- `stands and cannot be worked`: A fleet lock is on an issue no worker can be started on, so the fleet works nothing. `fix` gives the issue what it lacks; [`afkconvoy help humans`](help:humans).
- `the fleet's state cannot be read`: GitHub, the remote or the config failed to answer; `evidence` says which.
- `GitHub API fallback`: An explicit primary quota rejection, or a known zero remaining before reset, routes the operation to the other API under the same login. REST core and GraphQL observations are separate for each GitHub host and authenticated login. `doctor` reports them in `fleet.github_api`: `remaining: null` means unknown, `reset` is Unix seconds, and `for_rest_reads` / `for_graphql_reads` describe the current selection. Successful response headers update observations. A `github-api` line in the tick log records a fallback, its reason and any capability refusal. The APIs are tried at most once each, apart from bounded transport retries of reads; a later command can use the preferred API after reset without restarting the fleet.
- `REST cannot supply PR closingIssuesReferences`: REST can read complete issues, comments, native blockers, labels and PR heads. A complete REST enumeration with no same-repository open PRs lets an otherwise supported rebuild and eligible dispatch proceed. Any same-repository open PR requires GraphQL to establish its native closing relationships, including sidebar and cross-tracker links. Rebuild, dispatch, ordinary issue landing and settlement that need those relationships stop until GraphQL reset. A PR body, stale links and a failed read are never substituted for that relationship. Branch-only turns and watching PR heads do not require it. This does not promise recovery of every quota incident with existing open PRs.
- `GitHub primary quotas unavailable`: Both APIs are exhausted, or the remaining API cannot supply the operation's facts. The error names the operation, capability gap, known quotas, reset and next attempt time; it is a failed read, never a healthy empty frontier. Run the command again at reset. Plain 403s, missing permissions, invalid authentication and network failures do not authorize changing APIs.
- `GitHub secondary rate limit`: Both APIs wait for the server's `Retry-After`, including an HTTP-date value; without one they wait at least a minute. Switching APIs never bypasses a secondary or abuse limit. No command sleeps indefinitely on quotas: it reports the cooldown and the next tick retries when due.
- `write outcome uncertain`: A write is never retried after a lost receipt. Inspect the authoritative issue, comment or PR before retrying. A confirmed rejection of one REST API write can use a supported GraphQL mutation: issue creation/closure, comment posting, label creation, or adding/removing existing labels after reading their GraphQL identities. Comment edits and dependency writes identified only by a REST database id wait for REST reset. High-level `gh` writes can contain several HTTP operations, so a failing one is never replayed automatically. All original access, tracker and landing-turn constraints still apply.
- `harness is down`: Identical refusals hold claims and pause it; a prompt probes every {const:HARNESS_PROBE_MINUTES}m. Run `fix`.

## What `doctor` finds — warning: one issue or one patrol is held up

- `no fleet has taken`: A repo's ready issue has no open blocker or claim and has waited more than an hour, and its remote has no heartbeat within the 1800-second lease. Every host serving that tracker looks, including at repos absent from its checkout list. The host runner opens one report per repo, with its repo and escalate labels; only its opening host's watch asks the operator which host should take it. A claim on the waiting issues or a live heartbeat closes it and names the taking host. The watch never adds the repo to its checkout list.
- `remote could not be read`: A tracker, repo config, timing record or repo remote needed to judge a waiting issue could not be read. The evidence names the failed source; this says nothing about whether a fleet works the repo. Restore read access and let the next look judge again.

- `hot worker is past its limits`: A worker crossed a host resource limit. The watch receives its condition, duration, worktree, terminal and evidence and checks that work goes on.
- `admission has held back new workers`: One reason held admission for the host's span. The watch receives the host reading and evidence, once per episode.
- `the host has been under memory pressure`: Pressure lasted for the host's span independently of admission. The watch checks pressure itself, once per episode; it makes no worker hot.
- `under memory pressure from another account`: Pressure lasted for the host's span while another user account on the machine held the most resident memory, more than this account's processes, as the process table says it: that account and what it holds are named. A watch keeps away from another account's programs, so it starts none while this host's fleets hold no worker, nor once a watch has left pressure from that same account with the operator, until they answer its question or the largest holder changes — another account, or this one. Admission still holds new workers back under it. `fix` is nothing here: the other account's owner frees its memory.

A warning may be the fleet mid-step: run `doctor` again after a tick before you act on one.

- `ended at the exclusive bound`: A command held others up for the host's bound. Each occurrence in the last day has the command, runtime and number waiting in `evidence`. Run each step of a long measurement as its own `afkconvoy exclusive`. If a single gate or release build reaches it, check the host setting with `afkconvoy doctor` and change it with `afkconvoy run --exclusive-seconds N`, or `--exclusive-seconds default` to restore {const:EXCLUSIVE_SECONDS}s.

- `failed in tick`: A step failed, including a worker that could not start or take its brief. `evidence` is the error and `fix` is the line to try after correcting it: a failed dispatch can be run again, and a failed repair worker start uses `afkconvoy tick`. It stays visible across unrelated ticks until the step succeeds or the issue's work continues or ends. Three consecutive failed ticks make it critical instead.
- `its fleet instance is not alive`: Under `doctor --all`, a checkout on the checkout list whose fleet instance this host's runner does not hold, and that is neither broken nor holding claims nothing works, which have rows of their own. Nothing works its issues. Run `fix`: a `run` of the checkout starts it.
- `a tick failed since the last look`: Under `doctor --all --since`, a tick of the interval failed with what no unrecovered step's finding says: a step that failed and recovered before this look, or a tick whose line alone says `FAILED`. A tick held only by a failing cut need is not one: `not cutting here` says it. `evidence` is its errors; `fix` the line they name, else the plan.
- `worker's goal misbehaved`: Under `doctor --all --since`, an issue updated in the interval has a work account whose worker of a harness that keeps a goal — Codex — ended with its goal `budget_limited`, or took goal turns after its verdict stood: it did not mark its goal complete at its verdict. `evidence` names the account, what its `goal` says and the session record it was read from; `fix` shows the issue. Open a ticket from that evidence: the goal's objective, its budget or the fleet's ending of it is to change.
- `its health observation is overdue`: Worker health did not observe a worker, or observe it again after a failed observation, within its time and a tick's chance to: the sleep and the time of the last tick of the fleet instance whose claim holds its worktree, or the longest any instance on the host says. A fleet that stopped ticking, or a tick that hangs, leaves it overdue. While a fleet lock stands, its fleet leaves alone the workers of claims the lock keeps it off, and observes none of them: their observations are not overdue, and once the lock is closed one past its time is found again as before. A worker of a checkout that has left the checkout list is not overdue: no fleet ticks for it. A worker no claim holds any more, whose harness has ended — no process started with its `TMPDIR` is left, though its terminal may stay open at the shell — is retired by the next tick of any fleet: one of that fleet's repo when no claim of any fleet instance is on its issue, one of another repo when that repo's checkout has left the checkout list. A worker whose claim is still held is nudged, continued or escalated as before. `evidence` says when it was due and its error; `fix`, `afkconvoy kit`, shows `worker_health`. The watch starts on it.
- `has no worker`: A claim's worker is gone; a tick starts one. `fix` is for a claim it leaves so.
- `has been stopped for`: A worker is silent and its claim is still at work, judged by the same read the tick routes it from — doctor keeps no clock of its own. It stopped, declared nothing, and showed no sign of life for the grace period; one waiting on background work of its own — a shell or a monitor its harness shows, or a command of its in the exclusive queue — is not silent until that work runs past the gate limit, and then is at once. A dispatch whose worker has not taken its brief is never silent. Read its terminal; `fix` is the command the tick runs next for it: `nudge` for a worker with no PR due its one nudge, `tick` otherwise — the tick nudges a worker at a stage or landing, and restarts or escalates one silent past its nudge.
- `its session says its worker works, and orca says it is done`: A claim's worker has a turn still open in its harness's session, while orca has reported its agent done for the grace period. The tick routes a worker by its session and leaves one at work alone, so the claim waits for good while the two disagree; `worker.state` in `doctor` is `disputed`, not `busy`. `fix` tells the worker to carry on: for a landing, to run its turn again.
- `settling has waited for its worker`: A landed or closed issue's worker is still busy, still ending after settle closed it, or a process is in its worktree after the worker health grace of {const:GRACE} seconds. Settle waits without failing the tick and retries on later ticks; the finding names the worktree, worker state and processes. Inspect the worker and processes, then let a tick settle it once they leave.
- `waits on a blocker no fleet works`: The blocker is outside the tracker, or no single `repo:` label names a checkout serving it. `plan` and `doctor` name the waiting issue and the blocker, with the transfer line where needed and the label line. Run `afkconvoy flows` in the target checkout to choose its flow label. A named consult or declared hand-off proceeds when these are the only blockers; build work still waits. Transfer with `gh issue transfer <n> <tracker> --repo <its repo>`; use the new number GitHub assigns when applying the labels.
- `worker health is waiting for the operator`: A worker stopped past the observation bound, and neither the rules nor Jev — where the host settings name a Jev key command — classed it: there is no key command, it failed, TypeSafe failed, or Jev's answers settled nothing. `evidence` is that reason and the last line of its screen; `fix` names a key command where there is none, else the worker's screen to read. The watch starts on it. An hour on unchanged evidence escalates its issue.
- `the last tick started no worker`: The frontier is not empty, admission held nothing back, and nothing was dispatched: `evidence` is the tick's line, and `fix` the step that failed or the dispatch by hand.
- `follows no workflow of the team`: An issue's flow label names no workflow, or it has two. `afkconvoy flows` lists all.
- `longer than its baseline`: Nothing is wrong yet: an issue has been at one stage for long. `fix` shows it.
- `is one rework from a breaker`: The next `reject` escalates the issue. Nothing to do yet: [`afkconvoy help humans`](help:humans).
- `no harness can start this host's watch`: A look of the host runner called for a watch, and no harness of the host kit could start it or go on with it: each paused, with a fault on record, or failing to start, as `evidence` says. Nothing watches the host until one can. `fix` is one command, `afkconvoy kit`: it shows the host kit, and its `worker_health` the faults. The next look tries again (`afkconvoy run --help`, WATCH).
- `the resident watch is busy; its round remains undelivered`: The host's watch is in its session and this round has not been delivered. No replacement is started and the round's work is retained. The next look delivers it once the session can take input. `fix` is one command, `orca terminal list --worktree path:<watch-directory> --json`, naming that watch's directory. A host kit whose `paused` list or `worker_health` leaves no harness that can start uses `no harness can start this host's watch`, and that row's `fix` is `afkconvoy kit`.
- `is paused on this host`: It refused every prompt: no worker starts on it till an hourly probe answers.
- `has unplaced models in the host kit`: The watch researches these listed models with its web tools and places or settles them through `afkconvoy kit --research <file>`. `afkconvoy kit --help` gives the checked JSON format and research states. Omitted models still await research; a harness with none placed runs its default model. Research runs during a watch started for other work, or starts one alone at most once a day. A malformed file writes nothing and names what to correct.
- `differs from the agent setup`: The host settings declare an agent setup (`--agent-instructions`, `--agent-skills`, `--agent-guards`), and this harness of the host kit does not hold it as declared: its global instructions are not a link to the declared file, a skill the list names is not installed for it, one installed for it through `npx skills` is not on the list, or its hook settings (`~/.claude/settings.json`, `~/.codex/hooks.json`) miss a declared guard or hold one of the kit's the guard list does not name, as `evidence` says. `fix` is `afkconvoy kit`: writing the host kit gives every held harness the setup, links its instructions (what stood there is kept beside it as `<name>.before-agent-setup`), installs the list through `npx skills` and removes what the list does not name, and wires the guards, leaving every other entry of the hook settings as it was. The installed copies in `~/.agents/skills` are read-only between syncs; edit a skill at its source and run `afkconvoy kit` again. With no agent setup declared, nothing is given and nothing is reported.
- `Guild machine has no tmux`: This host is a Guild machine — its user has Guild's home, `~/.guild` — and neither a login shell's PATH nor `~/.pixi/bin` holds a tmux. Guild runs each instance in a tmux server of its own, and `guildd install` fails without one. `fix` is `afkconvoy kit`: writing the host kit installs tmux where a standard account can, with `pixi global install tmux` (into `~/.pixi/bin`), or `brew install tmux` where Homebrew is at `/opt/homebrew` or `/usr/local`, which have bottles; a Homebrew in `~/homebrew` would build tmux's ncurses and openssl from source and is not used. Where neither is there, writing the host kit installs pixi itself first — the release of the version it pins, checked against the `.sha256` published next to it, into `~/.pixi/bin` — and nothing where the checksum differs; `fix` is `afkconvoy kit` either way. A tmux already there is left alone.
- `names no model the host kit holds`: A team's roster names a model by a name that matches no model the host kit holds for its harness, by its id or any other name; `evidence` gives the nearest names. The fleet never changes a roster: a tick opens one issue for it in the team's repo, which the team's own fleet works. `fix` is the file and key to correct.
- `has no harness on this host it holds limits for`: A role holds limits for no harness the host kit holds, so no worker of it starts and its stages wait; the rest go on. They go on by themselves once the host kit holds one: `afkconvoy kit`, or write the role's limits for one it holds.
- `names a harness no worker of this checkout starts on`: The checkout names a harness, and a role holds no limits for it, or that harness cannot start. No other harness is started in its place. `evidence` names the checkout, the harness and why. `fix` writes the role's limits for that harness, or clears the name with `afkconvoy run <checkout> --harness default`, or restores the harness with `afkconvoy kit`.
- `matches nothing in the host kit`: A role's roster entry names only harnesses or models this host lacks, so the role runs the host kit whole, less what it holds no limits for. Add one with `afkconvoy kit`, or change the roster.
- `does not run: its last run failed`: The issue that reports a patrol's failed run is open. Look, then close it: `fix`.
- `not cutting here`: A due cut's host checks failed. `evidence` names each failing now and one user-only file of their stderr lines, kept while the cut stays held. One held cut is one finding, whichever need fails. Check the repo's `cut-needs` declaration and the host's access; another host that passes them can claim the cut (`afkconvoy config --help`).
- `wait on the next cut`: These issues' workers declared `blocked` on the next cut (`--blocked-by cut`, or `blocked_by=cut` in an unbound repo's verdict): each needs a version of this repo that is not installed yet, and carries the `convoy-waits-on-cut` label, off the frontier. They hold no claim, so the fleet can go idle and cut. `evidence` says where the cut stands. Once a cut has published and installed its version it takes the label off them and they return at the stage they left; a failed cut leaves them waiting until it is answered. Nothing is to be done but let the cut run; taking the label off by hand starts them again at once.
- `install failed on this host`: A gate or cut need declares an `install`; this host ran it after the check failed, and the check still fails. `evidence` says when it ran, how long it took, its status and the user-only file of its last 20 stderr lines. It is not run again for an hour unless its declaration changes. Fix what the file names, or the repo's install (`afkconvoy config --help`).
- `was installed on this host`: A gate or cut need's `install` ran on this host and its check then passed. `evidence` says when and how long. Nothing is to be done.
- `cuts no version: its last cut failed`: The issue that reports the fleet's failed cut is open, under the label `convoy-cut-failed`: the host's watch answers it, and a look that finds it starts one, whether or not the rest of the fleet moves. `what` names the version and the step that failed, `evidence` the issue and why, and `fix` how the cut starts again from this host: where its checkout is kept here, the `cut --from <step>` line that goes on from that step and closes the issue; where it is kept on another host, that line there; where it is gone, or a fix had to land first, closing the issue, so the next idle tick, or busy tick past the age bound, cuts again from the start on the base tip. It also says the fate of the branch the cut pushed: one standing on the base tip is taken up by that next cut and stays; one on an older base is taken up by nothing, and `fix` gives the line that deletes it. Where what failed it is one of the four human kinds (`afkconvoy help humans`), the watch swaps the label for the escalate label, and it waits for a human.
- `` have reached its `max_open` ``: A patrol is not run while that many of its issues are open. Close some, or raise it.
- `has waited for a human for`: Nothing in the fleet moves that issue. `fix` answers it: [`afkconvoy help humans`](help:humans).
- `human decision sending has failed repeatedly`: The host's notify command failed {const:NOTIFY_FAILURES} times in a row for one condition episode. `doctor.host.notify` says the command and last sending. Correct the command with `afkconvoy run --notify-command <COMMAND>`; the next look retries. `default` disables sending. A sending command has {const:NOTIFY_SECONDS} seconds and holds back no watch round, look or tick.
- `a watch round's daybook entry is not written`: The host runner could not append a reported round's entry to the daybook (`afkconvoy daybook --help`): the tracker has no `Daybook` discussion category, its discussions are off, or GitHub refused. `doctor.host.daybook` holds each entry still queued, its failures and its last error. Fix what the error says; the host runner retries by itself, waiting longer after each failure, up to {const:DAYBOOK_RETRY_MAX} seconds. It holds back no watch round, and the round's human questions still reach the asking session.

- `is held off by a PR not the fleet's`: No worker starts: it would open a second PR. `fix` closes it, or merge it yourself.
- `is claimed but GitHub has it no more`: Deleted, transferred, or no such issue: its fleet's next tick releases it. `fix` is for one stopped.
- `the gate is slow`: On one host, the last {const:SLOW_GATE_LANDINGS} landings with a recorded gate run all exceeded the fixed `gate_budget_seconds` when declared, or took more than {const:SLOW_GATE_PERCENT}% of the termination gate limit otherwise. Queue waiting is excluded. A warning never ends a gate. Compare the gate logs against the committed baseline: step wall times, Flux functions, and nextest slow tests with full names and seconds; parallel test durations are not gate wall time. A tick opens one issue for the fleet to make the gate faster: `fix` shows it. Raising `gate_seconds` or `gate_budget_seconds` is no fix, nor is deleting or skipping tests.
- `the host runner did not move onto`: A newer release is installed where the host runner was started from, and it did not start, does not say its version, or the wait for ticks and a running exclusive command to end exceeded ten minutes: `evidence` says why, including which ticks or command held it. The host runner works on, on its own release, and tries that file again once it changes: install it again (`brew reinstall afkconvoy`), and `fix` shows whether it now says its version.
- `is published, newer than the host runner's`: The Homebrew tap the host runner was installed from publishes a newer release than the host runner runs, and the host runner has not moved onto it yet: `what` names the release Homebrew has installed and the published one. The host runner installs it itself, at its look after the one that found it, within twice {const:PUBLISHED_LOOKED_MINUTES} minutes of `evidence`'s first seen, and then moves onto it (`afkconvoy run --help`). `evidence` says why the last `brew upgrade` failed, if one did: `fix` runs it by hand. The host's watch leaves it alone: its `brew` would race the cut's own install on the host that cuts.
- `is first on PATH`: The `afkconvoy` a shell finds first on its PATH is not of the release this account's host runner runs — or, where none runs, the one this `doctor` is: an `afkconvoy` typed there is another than the fleet's, as an older one in a Homebrew prefix shared with other accounts can be. `evidence` is the PATH `doctor` was run with, and `fix` lists every `afkconvoy` on it: put the directory of the fleet's first, or remove the other. The host's watch leaves it alone: a shell's PATH is its user's.

## What `doctor` finds — info: nothing is held up

- `which is ignored`: A concurrency is still named — kept with this checkout on the checkout list by a `run --concurrency`, or named by the repo config — and nothing reads it: no number bounds a fleet's workers, and admission alone decides each start (`afkconvoy run --help`, ADMISSION). Nothing is held up. `fix` is `afkconvoy run <checkout> --concurrency default` for the checkout's, or deleting the key for the config's.
- `moved since the stage`: A role or the team was pushed after a stage started: that worker goes by the older one, the next stage by the head. `afkconvoy doctor --help` says what moved is.
- `declares no gate limit`: The config sets no `gate_seconds`: the gate may run {const:GATE_SECONDS} seconds before anything ends it. Set it to the most the gate should take: `fix` names the file and key.
- `human wait is taken by`: Another host's watch holds this wait on the repo's remote and its heartbeat is within the lease. Leave it to that host. It starts no watch round, sending through `--notify-command` or asking-session question here; the next look can take it over once its holder is past the lease.
- `is kept with no claim`: A worktree holds what the remote lacks, or an earlier release kept it. `fix` removes it, pushing first what only it holds: read `what` before you run it.
- `is kept after its claim was taken`: Another host holds the issue's claim, and this host's worktree still holds work the remote does not have. The tick closes its worker's terminal and keeps the worktree, pushing nothing. `fix` lists the local commits for a human to inspect; preserve them separately before removing the worktree. A worker's `verdict`, `land` and `gate` refuse while that other host holds the claim. A restart on this host keeps its workers.
- `works on this machine under another account`: This account has no host runner, and another account on the same machine runs one: each account is a host of its own, with its own checkout list, host kit, exclusive lanes and panel, so the fleet you look for, and the findings that would set up a second one here, may be that account's. Said with its account, pid and what that account's processes use of the machine's cores and memory, read from the process table alone. `fix` is its `doctor --all`, run as that account.

## What a start refuses with — `plan`, `tick` and `run` check first, and start nothing

- `this host cannot work a fleet yet`: What `doctor` finds on a host, said at once: run each line after a colon.
- `cannot read the config file`: The repo has no config on the branch checked out. `afkconvoy config --help`.
- `the remote has no branch`: The config's `base_branch` is not on the remote. Push it: the fleet creates none.
- `is public: anyone can comment on its issues`: The checkout's tracker — its own repo, where it says none — is public. Say a private one with the line the refusal ends in, or make it private.
- `that push would be refused`: The base branch's protection requires a PR, checks or a named pusher, and a landing turn ends by pushing. Lift the rule, or pick another base branch.
- `the remote rejects the fleet's refs under both`: The remote takes neither hidden refs nor `convoy-*` branches, so no claim can be kept. A push rule of the remote's is what refuses: lift it for one of the two.
- A missing worker launch command is discovered automatically for a known harness in the worker's login shell and merged into the latest host kit. If resolution fails, install the named program or fix that shell's PATH. If login or required flags fail, follow the named harness's login command or update its explicit command in the host kit. An explicit command is never replaced by a default; running fleets read kit edits at their next worker launch.
- `cannot read the host kit`: Run `afkconvoy kit` on this host, or `run`, which writes it where there is none.
- `--worker-command is gone`: Run `afkconvoy kit` to edit this host's worker launch commands.
- `is no harness`: Use claude-code, pi, codex, dsh, kimi or grok.

## What neither says

- **An issue is not worked**: `afkconvoy plan` has it under `excluded`, with why. Remove what the reason names.
- **A changed role or team did not reach a worker**: It is not pushed to its default branch, or the stage had already started.
- **The labels were moved back, and the issue escalated again**: A label is not where an issue is: [`afkconvoy help humans`](help:humans).
- **A stage's verdict counted for nothing**: Its record names another stage than its claim was for. `afkconvoy show --issue <n>` says how each record was read; `afkconvoy send` puts the issue where it belongs.
- **Another host's fleet died**: Its claims go stale by themselves and are taken. Or: `afkconvoy takeover --help`.
- **Everything must stop now**: SIGTERM the host runner (`host_runner.pid` in any `run`'s answer), then close the workers' terminals in orca. Every issue keeps its labels and stage records: a later `run` goes on from where each one was.
