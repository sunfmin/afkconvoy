A team's roster says what each of its roles' workers may run: which harnesses and models are eligible; the host kit supplies their order. Read this to write one, to see why a worker started on the harness it did, or to see why a role's stages wait.

## The roster

The `roster` of the team file ([`afkconvoy help team`](help:team)) holds an entry per role it names, by the role's short name:

```yaml
roster:
  dev:
    cast: Hard or wide work on fable; the rest on opus.   # accepted, ignored by a start
    run:                           # one at least; eligibility, not priority
      - { harness: claude-code, model: opus, good_at: most work }
      - { harness: claude-code, model: fable, good_at: hard or wide work }
      - { harness: pi }            # any model the host kit holds for pi
  reviewer:
    run: [{ harness: codex, model: gpt-5.5 }]
```

Each of `run` names a `harness` — claude-code, pi, codex, dsh, kimi or grok — and may name a `model` by any of its names on that harness — its id, as the host kit holds it and `afkconvoy draft` writes it, or another name it answered to, whatever the case, the provider prefix left off where that leaves one match (`afkconvoy kit --help`) — and `good_at`, what the host kit's research says it is good at. `afkconvoy draft` copies good_at from that research and sends no prompt. No human edits the host kit to supply it. One that names no model allows any model the host kit holds for the harness, or the harness's command as written where the host kit holds none. `cast` is accepted and ignored: a start does not read it, and `check` does not fail on it. A role the roster names no entry for may run whatever the host kit holds, but a harness it holds no limits for (below). A model an entry names that matches none the host kit holds for its harness is cut from the range: `check`, `plan` and `doctor` name the entry, what the host kit holds and the nearest names, and a tick opens one issue for it in the team's repo, with that repo's ready label, for the team's own fleet to correct — none while one for it is open. The fleet never changes a roster.

A roster is drafted rather than written from nothing: `afkconvoy draft`, in a checkout of the team, writes one into team.md from this host's host kit — each role's `run` in the host kit's order, with `good_at` from the kit's research, and no `cast` line — and commits nothing. It sends no prompt. A human reads it, edits it and commits it; the fleet never changes a team's roster.

## A role's range

On a host, a role's range is its entry cut to the host kit (`afkconvoy kit --help`), in the host kit's harness and model order: a harness, or a model, the host kit does not hold is left out. An entry the host kit holds nothing of is not followed: the role ranges over the host kit whole, as if the roster named none for it, and `check`, `plan` and `doctor` name the entry. So is a harness the role holds no limits for while it holds limits for another: no worker of the role runs a harness it holds no limits for, and a host kit may hold every harness its host can start. `afkconvoy check` and `afkconvoy plan` name each harness a range leaves out, and why (`no limits for pi`). `afkconvoy check` answers each role's entry and its range on the host it runs on; `afkconvoy show` draws the roster under the workflows.

## An issue's model label

Automatic casting is gone. `afkconvoy cast` and `afkconvoy kit --cast` fail and say so. No worker is started to choose a model, and no issue waits.

Every worker chooses the first eligible harness in this machine's host kit order; its role's range and limits remain constraints. A `harness:` label never selects a harness. `switch --harness` reorders the kit. `switch --model` moves a model first inside its harness and does not choose the model a worker starts on.

A worker's model is the issue's one `model:` label when that label names exactly one model of the harness already selected and the role's range holds it, matched by its id or any name. The worker starts on that model's id. The label is left as written. Otherwise the worker runs that harness's user default, and the label stays: no `model:` label, a name that matches nothing or two models, two `model:` labels, or a model the range does not hold. A label that is not followed is said once on the issue, with the nearest names or the two ids, and the worker starts on the user default in that same dispatch. Nothing is taken off the issue.

Claude Code, pi, Kimi and Grok start with no model flag. Kimi then uses the default in the user's Kimi config. DSH starts with no model in the worker environment, so the profile's model runs. Codex reads `model` from the user's Codex config when that value is a nonempty string the host kit lists, and passes it; with no such key it starts with no model flag. A Codex model the kit does not list, or that is not a nonempty string, refuses the start. One outside the role's range refuses too. An unnamed default cannot be checked against a range, and the worker starts.

A watch, a cut and an inspection have no model label and use the user default. A landing worker follows its issue's label by the same rule. A range that holds one model does not name it: with no followed label the worker still runs the user default.

`afkconvoy switch --harness codex` moves the Codex entry first. A known installed harness the kit does not hold is added first with no model, starts workers on its login's default at once, and is listed and researched only after the answer, with no model probed; that later refresh keeps the switch's order. Its newly listed models are `research pending`, and no worker starts on them until research places them. An added harness that cannot start is reported by the switch and `doctor`. `afkconvoy switch --model sonnet` moves that model first within its harness, and its harness first in the kit; it does not choose the model a worker starts on. Its listed id or any of its names matches. Ambiguous names and names the kit holds no placed model for are refused with candidates or nearest names. Other entries and contents stay intact. Every checkout follows these orders; no instance or checkout is required. With no target it leaves existing workers alone. `--all` continues workers across the host's checkout list, preserving their scene and reporting failures separately. Every moved worker's answer and tick-log line explain each earlier skipped harness and what would make it eligible. Change priority by switching again; `--clear` is removed. Old repository choice files are ignored.

Rebuild, daily refresh and new-model research preserve established harness and model order. An unavailable or paused candidate is skipped without reordering; a successful recovery probe makes it eligible again. Fault recovery keeps claims and work, and classes structured signals and an explicit harness usage-limit message by rule first, with or without a key. Where the host settings name a Jev key command, Jev judges what else a stopped worker's screen shows, and the screen is sent to TypeSafe; no harness is asked. Without a key, or where the command, TypeSafe or Jev's answers settle nothing, the worker waits for the operator and the watch: `doctor` names it with its reason and a line of its screen. Account quota without a reset continues at once; unresolved waits on unchanged evidence, the operator's among them, are bounded to one hour, then escalated with evidence. Plan, doctor and panel say whether a model label was followed or the user default was used, and the model a running worker was started on. They report no caster and no host cast flag. `needed` is false and `skipped` is empty.

Every tick reads each worker's turn from that harness's session for its worktree; whether a terminal is live still comes from one host-wide `orca worktree ps`. An open turn is healthy without screen judgment, however long the screen has been quiet. A failed delivery still goes to classification once the session records that the turn ended. `done` with `mainAgent.outcome: failure` is stopped at its first observation: classification rules run at once, then Jev or the operator where no rule decides the fault, without waiting for two screen observations. A turn ending without failure follows the existing finished, verdict and nudge logic. Orca's `agentType` decides the harness for a continuation or pause when the recorded harness disagrees. Doctor and the panel show each observed worker's Orca state, outcome, agent type and `stateStartedAt` (epoch milliseconds), and name a wrong harness record. Termination is confirmed by a fresh runtime read before any replacement starts.
