# A turn lands its PR on its target branch

A turn makes the PR's merge commit on the current target tip, gates that commit, records green, and pushes that same commit to the target branch as a fast-forward. This replaces the landing train of ADR-0004 and the joining step of ADR-0034. The train added no verification after a recorded turn, but needed another worker and a separate lane; the measurements in ADR-0034 show the cost of running those gates together.

A cut's landed commit has one parent (sunfmin/control#178). The turn builds it on the base tip as it stands, gates that tree, and fast-forwards the base branch to that same commit. Its diff against its parent is what the set lines wrote; where the base moved, the parent is the tip at land time and the landings already on it stay. The commit that set the version stays on the cut's branch and is not an ancestor of the base. Issue turns and watches still land as merge commits. A commit with one parent whose subject ends ` (#n)` and whose message has no `By a cut on <host>` line is not a landing. Tags already published stay where they are.

## Pinned task destinations (sunfmin/control#154)

An issue turn resolves the task's immutable target record before reading its PR or recovering a landing (ADR-0006). The PR's actual base must equal that target, before any already-landed shortcut and again before publication. A base changed during validation invalidates the candidate. Existing source-head verification, green evidence, expected predecessor and atomic publication checks remain required. Each target has its own `candidates/<branch>` record; no candidate or settlement walk uses another target's history. The configured base alone supplies the landings that trigger a cut.

Certification reads the gate declaration from the selected branch's tip, but retains the selected branch identity even when that declaration still names another `base_branch`. Red markers and repair claims name the affected branch; the repair issue is pinned before it receives dispatchable labels. A repair for another target cannot bypass certification even if the two tips have the same commit. Abandoned-candidate cleanup, doctor and the panel inspect all branch chains and identify their targets. Host worker lanes and repo leases remain the same scheduler and exclusion boundary.

Red, a conflict, or a rejected push ends the turn without landing. A conflict with the landed base stays in the worker's worktree. A rejected push requires another turn. Only worker lanes remain; independently owned candidates of one repo may validate together as described below.

## Candidate validation and ordered landing (sunfmin/control#131)

A cache configured inside a checkout, including another repo's, is refused before reserving a turn or assigning a candidate. The operator sets `XDG_CACHE_HOME` outside every checkout; the command never silently moves onto another host cache.

Candidate worktrees live under the host's cache at `candidates/<repo-key>/<candidate-id>`, keyed by the canonical common git directory (sunfmin/control#453). They must be outside the checkout: tools that walk up for configuration otherwise read the checkout's branch above the candidate's commit. In particular, a candidate under `<checkout>/.git/convoy-candidates` can find a tsconfig whose globs exclude that candidate. Removal recognises both the new root and that earlier common-git-dir root, and only a candidate's exact directory in either root; retained candidates from an earlier version are removed when they stop.

The approved change replaces whole-turn same-repo exclusion. Given certified base M and original PR heads A, B, C, turns assign A1=merge(M,A), B1=merge(A1,B), C1=merge(B1,C). Each immutable candidate has its own detached worktree. The source branches and their original heads stay intact, so a cancelled successor can rebuild from M+B without carrying failed A back in.

One remote ref, `candidates/<target_branch>` under the settled ref layout, holds the candidate chain. Its commit message records each candidate's identity, original head, predecessor, merge commit, tree, gate declaration, owner and gate process identities, validation state, cancellation cause and gate result. Its first parent is the previous record, and its other parents preserve candidate objects and source history. A candidate that has ended, whose owner is observed gone and whose worktree is removed, is not carried into the next record unless a candidate it keeps stands on it or was cancelled by it: the record stays bounded by the candidates still held, and the earlier records, its first-parent history, keep the dropped one's evidence and objects (sunfmin/control#308). The record goes to git on stdin, never as an argument, so the OS's `ARG_MAX` does not bound it. Every write is a normal fast-forward push: two concurrent assignments cannot both extend the same record. No runner memory is authoritative. An unreachable remote stops progress rather than authorizing an unobserved transition. A gate-record push that has not ended within 30 seconds is killed with its process group and reported as `not_recorded`; the candidate is not green, and its worker lane can pass to queued work (sunfmin/control#421).

The states are building, validating, green, landed, red, cancelling and cancelled. Assignment occurs after a worker lane is available and checks the bounded window again atomically. The window includes green candidates waiting on predecessors and cancellations whose process exit is unconfirmed. It is bounded by the host's worker-lane count; light gates retain one repo lane. A full window, an existing owner of the PR, an issue blocker or a barrier waits outside host capacity. Ordinary heavy commands retain same-repo isolation; another repo may use a free lane.

Green successors keep their recorded result while predecessors finish. Publication rechecks validity, the original PR head, the exact predecessor on the base branch, issue blockers, locks and the green record. One atomic receive-pack transaction advances the base and chain record and verifies the unchanged source head; cancellation and publication therefore contend on the same ref. A regular `git push --atomic` omits an unchanged source ref, leaving a source-head race between advertisement and commit. To local and SSH remotes the tool sends that explicit old-equals-new verification command, with Git constructing the pack: `git receive-pack` locally, the existing Git SSH login over SSH. GitHub's smart HTTP endpoint does not accept `gh api` authentication, and the authenticated Git HTTPS helper does not expose a raw receive-pack connection, so a GitHub HTTPS origin publishes through GitHub's `updateRefs` instead: a plain `git push --atomic` through git's credential helper carries the new objects to scratch refs in the repo's ref layout, and one `updateRefs` call checks every ref's old value — the unchanged source head included — and applies every update and deletes the scratch refs, all or none. GitHub answers a stale old value with no typed error, and a failed answer may follow a batch it applied, so after a failed call the refs are read again: all at their new values is published, all at their old values is an error, anything else is stale. A host with a GitHub HTTPS origin needs `gh` logged in and git's credential helper giving that login (`gh auth setup-git`), and no SSH key. No token is handled. An unsupported transport or failed authentication refuses before any update command is sent. Expected-old checks on all three refs and checked first parents keep both advances fast-forward only. The pushed commit is the candidate whose tree was proved green. No aggregate gate or newly synthesized merge is added. A known chain advance preserves successors; a chain-external base move or changed PR head invalidates the affected suffix.

A red result records the actual gate evidence and invalidates its entire suffix before cleanup starts. Local dependent process groups and descendants are stopped, killed and observed exited; gates on another host observe invalidation through the same remote record. Green completion cannot restore invalidated work. The cancelled command answers `cancelled`, names `cancelled_by` and `cause`, and incurs no gate failure or workflow rework. Its worker requests another turn using its preserved branch when semantic blockers permit. Failed work follows the existing fix-and-commit policy. Nothing blindly repairs or retries the failed PR.

A valid fast-green candidate whose gate processes are confirmed stopped is the exception to owner-death invalidation on the same host (sunfmin/control#459). Its next turn for the same PR and original head adopts its ownership atomically, leaving its identity, commit, tree, result and successors unchanged. There is no running gate to duplicate, and reusing the recorded evidence avoids cancelling a whole round because a waiting turn exited on a transient fault. A candidate still building, fast-gating or slow-gating, and every dead-host takeover, keeps the invalidation rules above.

A stopped candidate's worktree is removed (sunfmin/control#191). The worktree is where the gate ran, so it holds that run's build, and nothing reads it once the candidate has stopped. The evidence that stays is the candidate chain record: the phase, the cause, and the gate excerpt. A recorded gate run stays on the remote. Removal follows the record, for a landed candidate, a red candidate, and a cancelled candidate whose processes are confirmed gone. A candidate that is building, validating, green and waiting, or cancelling keeps its worktree. A process that still has the worktree as its working directory keeps it until a later tick sees that process gone. A directory left after git dropped the registration is removed the same way, including when a directory inside it is not writable by its owner. The issue's, watch's, or cut's worktree is not a candidate worktree and is not removed. The chain record is not rewritten.

A gate shell waits on a pipe until its process group is recorded; a parent dying before registration closes that pipe without starting the build. Kernel worker-slot leases are inherited only by the owned command. They survive runner and owner death while descendants remain, preventing replacement capacity before confirmed cleanup. Process identities include physical host, PID and precise kernel start time. An inherited scope descriptor identifies owned descendants even after reparenting or a process-group change; its kernel lock confirms their exit. A process group is signalled only while its leader's identity and scope ownership still match. A failed observation does not prove death, and a remote host's unconfirmed process is not silently replaced. A later request completes local interrupted cancellation; duplicate PR requests cannot create another writer. Publication records the landed prefix atomically with the base push, and base merge history also recovers issue settlement if the owner dies after that push.

Cuts, watches, fleet-lock repairs and base certification are serial barriers. A serial turn reserves a durable pending barrier outside worker capacity, blocking new candidate assignment while its predecessors drain, then removes that reservation atomically when assigned. It cannot starve behind a continuously refilled window. Inherited shared repo leases for candidates and exclusive repo leases for ordinary commands also preserve same-repo isolation after a runner restart. Red-base certification and repair rules below remain in force. The panel and doctor interpret candidate state through the same core lifecycle, showing predecessor, validation, capacity versus predecessor waiting, and cancellation cause. There is no separate train worker or train lane.

The normal core tests exhaust reachable interleavings of exactly three assigned candidates, green/red completion, invalidation, process exit confirmation, external movement and publication. This is a bounded state exploration, not a proof of arbitrary graphs or operating-system process semantics. Production uses the same lifecycle transitions; Flux separately checks publication authorization invariants without exemptions.

### Controlled candidate batch measurement

The ignored real-binary test `candidates::measure_serial_and_parallel_batches`, run through the host's exclusive queue on FelixMBP14.local (14 logical cores, 48 GiB RAM), compares the same three changes and gate command at one and three worker lanes. Version `0.5.22+159.g09fdc2d7` produced the following measurements. Each gate builds a private AWK array of 500,000 numbers and reads it in 40 passes. Each batch uses actual local Git remotes, candidate assignment and publication; its elapsed time includes that overhead. The gate's file timestamps provide the finer duration alongside its whole-second record.

| Worker lanes | Batch elapsed | A gate elapsed | B gate elapsed | C gate elapsed | Discarded gate time |
| --- | --- | --- | --- | --- | --- |
| 1 | 15.875 s | 3.758 s | 3.685 s | 3.768 s | 0 s |
| 3 | 6.533 s | 3.774 s | 3.741 s | 3.736 s | 0 s |

The parallel batch took 58.8% less time (2.43 times the throughput for this batch). Individual gate changes were +0.4%, +1.5% and -0.8%. This synthetic workload demonstrates overlap and measures contention for this workload; it does not predict the speedup of the repository's full build and Flux gate or separate CPU from memory costs. The controlled predecessor-failure test separately cancelled two live dependent gates, recorded 1 second of discarded gate time in total at whole-second resolution, confirmed child exit, and rebuilt without the failed change. No production failure was introduced for the measurement.

An unrecorded base tip is gated alone in a separate checkout, using its own gate declaration. Ordinary turns wait outside the worker lanes while that tip is red. The fleet opens a dispatchable fleet-lock issue for its repair, under an exclusive claim on opening it. An operator worker makes the repair outside product workflows, so even a workflow that begins with a human stage cannot hold it back. Only the fleet-lock repair issue for that exact red tip may take a turn on it, and it must still gate and record its complete merge commit before landing. The fleet's repair label and ready label make it dispatchable through the ordinary issue and claim protocol, with no human stage. The guard reserves the repair label to the fleet. A standing lock raised by an older release also remains eligible to land its repair without waiting for a green tip.

An older train line is migration input only. A green tip can fast-forward the base with its existing record; otherwise each PR takes a turn. No new line is written, and the old line is removed only when its work has been accounted for. The host watch (which replaced inspections in ADR-0035) and cuts use the same turn as issue workers.

## Evidence before removing the train

On FelixMBP14.local, 0.5.21 is the first released version holding sunfmin/control#110. The host runner log records installation at 2026-10-26 11:55:51 UTC and its start on 0.5.21 at 11:56:40 UTC (pid 63495). The tick log read was `~/.cache/afkconvoy/runs/afkconvoy-6f54123d7451f999.jsonl`.

The initial afkconvoy-repo read through 11:58:18 UTC found no train-lane gates or repairs there. A host-wide audit of every `runs/*.jsonl` from that runner start through 2026-10-26 12:57:08 UTC found exactly these train-lane gates:

| Repo / issue | Started UTC | Why it ran | Result |
| --- | --- | --- | --- |
| hostvitals / control#55 | 11:56:44 | `gate the train's tip`: the tip had no green record; the request survived the host-runner upgrade | Green, exit 0 after 58 seconds; #55 then took its worker turn at 12:09:02 |
| bizkernel / control#109 | 11:57:48 | `gate the train's tip`: no green record for `a265af37f9b9e650b4ee77d7497dec6c9d28adf3` | Red, exit 1 after 153 seconds; the repair then waited for the green tip its own fix needed to produce |

There were **no train-worker repair runs** in that window: no train `land` returned `gate_red`, and no train worker made a repair. The watch instead fixed the lock-turn deadlock in [PR 539](https://github.com/sunfmin/afkconvoy/pull/539); its evidence identifies the bizkernel failure as a Flux solver timeout in `abi::Manifest::read`. That repair protocol is retained here, including standing locks raised by an older release. A repair's turn must not wait for the green base tip it exists to restore.

The replacement covers both observed missing-record certifications in a separate checkout, in worker lanes. It covers the red-tip case with the operator repair and its own turn. Unrecorded legacy history, including old worker fixes with no surviving issue PR, is preserved through recovery PRs. Earlier afkconvoy train landings at 11:44:22 and 11:51:08 UTC ran on 0.5.20; they are not observations of #110.

Legacy recovery is resumable through issue-linked Orca workspaces. Conflicts and red gates retain those workspaces for a worker; retries reuse them. Migration returns on a red base instead of blocking the tick that must dispatch its repair. A final recovery PR preserves the original line's history, including a closed or rewritten PR head and commits an older train worker made.

## Rounds (sunfmin/control#240)

Amended by ADR-0048. Where a candidate's commit declares a fast gate and a slow gate (ADR-0047), the candidate is validated by the fast gate, and its green does not land it. A **round** runs the slow gate once, on the commit of the chain's tip, when every candidate of the chain is fast-green, and its green lands every candidate up to the tip in the one atomic publication described above, which now verifies each of their source heads. That is an aggregate gate, which this ADR had none of: it is the one gate of more than one candidate. A candidate whose commit declares no gates keeps every rule above.

## Fast gates (sunfmin/control#237)

Amended by ADR-0049. Same-repo isolation holds for ordinary heavy commands, but not between fast gates: a worker's fast gate runs in the fast lane, beside the other fast gates of its repo up to the host's `fast_lanes`, each in its own worktree, and takes no repo lease. A landing turn's fast gate is part of the turn and keeps the turn's worker lane.
