# Crates other programs may depend on, and Guild replaces the fleet

afkconvoy is to be replaced by Guild, another program of this host's user (decided 2026-11-12, sunfmin/control#693; Guild's side is in sunfmin/guild's `docs/adr/`). What is replaced is the fleet: its team, roles, workflow, claims and patrols. What took long to get right and is not the fleet's — how each harness is started and read, how a repo is gated and its heavy commands queued, how a change lands, what is given to a machine, how busy a host is, and the daybook's format — stays, as crates Guild depends on. Guild may use afkconvoy only as crates, never as a program it runs (sunfmin/control#811).

Until the replacement is done, a repo belongs to one of the two alone: one whose truth is GitHub, or a host's local tracker (ADR-0091), is afkconvoy's; one whose truth is Guild's Forgejo is Guild's. When a repo moves is Felix's to decide.

## The rule every such crate keeps

- **One home.** A rule or a format both programs need is spelled once, in its crate. afkconvoy-core re-exports what the core needs, and the cli calls it; neither keeps a copy.
- **No fleet concept in its API.** No team, role, stage, issue, claim, patrol, intake, tracker, worker or watch type appears in a public item, and the crate depends on neither `afkconvoy-core` nor the cli. What a program notes beside a fact of the crate is passed in neutrally — a ticket's or a candidate's `note` of the program's own type, which no rule of the crate reads — and what only the program knows it says through a trait it implements. A test of each crate from outside checks it depends on nothing of the fleet.
- **A git dependency pinned by revision.** Another program depends on a crate as a git dependency pinned to a revision of this repo, the one it was tested with. No crate is published: a pinned revision is reproducible, and nothing outside this host's user depends on them.
- **A change to a crate's API is a change to another program's dependency.** It stays neutral: a fleet fact it needs is noted beside it, put in the start's environment, asked through the program's trait, or mapped by the core.
- The pure crates — harness, gate, landing — keep their Flux refinements (ADR-0007); `./verify.sh` checks them as the core's dependencies, and the gate holds them to no function taken on trust. The crates that are effects on a machine, a kernel or a store — host kit, host reading, daybook — are not checked by Flux.

What each crate holds, module by module, is its `lib.rs`'s to say; this records why each is a crate.

## The crates

**Harness** (`crates/harness`, `afkconvoy-harness`). What afkconvoy knows of each harness: how one starts, where it reads its rules and skills, how a hook reaches it and is answered, where it keeps its session and which lines start or end a turn, what its usage lines count, which screen words mean a quota, a limit or a refusal, and the engine accounts (ADR-0086). A flag, a path, a hook event or a session format of one harness is spelled only in its module (ADR-0042). A session starts from a neutral `Start`; the core maps a worker's start in its role onto it. Some of the crate serves Guild alone — a soft stop of a session, its status from hook events, its steps, a user configuration directory of its own per instance — and afkconvoy's own workers use none of it; afkconvoy's workers leave Claude Code on the host user's configuration.

**Gate** (`crates/gate`, `afkconvoy-gate`). How a repo is gated (ADR-0047) and its heavy commands queued (ADR-0019, ADR-0057, ADR-0088): the gate a repo declares, a run judged and its record and ref layout, the slow-gate judgement, the exclusive queue's tickets and lanes, and the queue's `holder`, which one process of a host embeds — afkconvoy's host runner, or Guild's daemon. What only the embedder knows (the time, its lanes, what is shown of a ticket, how an asker reaches it, the command that enters the queue) it says through `Host` and `shell::QueueCommand`. What a run writes and reads back goes through `Records`; the crate's own `Git` lets a program with no runner of its own run a gate. The issue a slow gate is reported in and the comment a red run leaves stay in the core. afkconvoy's own effect half — its gate runner's cancellation, process groups and retried pushes — stays in the cli, tied to its candidates and host settings.

**Landing** (`crates/landing`, `afkconvoy-landing`), on the gate crate, with the forge behind an interface. Candidates and the candidate chain, rounds (ADR-0083), leases, what a turn on the chain does next, and the publication authorized from what was just observed (proved by Flux). Landing is plain git: a turn merges, gates, records and pushes a fast-forward, and never asks the forge to merge, since a forge's merge is not the exact commit the gate passed. What a turn needs of the forge — the change as the forge has it, what is noted beside its candidate, its landing commit's message, whether it may land now, what follows once it landed — is the `Forge` trait the landing program implements: afkconvoy's is GitHub's pull requests, in the cli; Guild's is Forgejo's. A change is recorded by its number under the key `pr`. The crate's `Lander` is a plain-git runner for a program with none of its own; it carries on what an earlier run left (a valid candidate taken up, a dead owner's taken over) and names a refused publication `Unpublished`, never `Waiting`. afkconvoy's own runner of a turn stays in the cli, with what only a fleet host has — lanes, a gate's process group owned across turns, adoption of a fast-green candidate, a base tip certified alone — and decides nothing of its own. afkconvoy keeps its chain in the host's database and the `Lander` in a store on the host the program names, neither on the remote (ADR-0117): `turn::publication` is what a publication updates, the target and every member's source head, with no chain record. The proving branch and its promotion (ADR-0090) are the crate's too (local/macnomac-studio#31): a `Lander` that names its proving branch gates what lands there by the fast gate alone, the one rule of which `proving::proves_on` and `proving::landing_gate` spell; and `proving::promote` is the one promotion — both tips read, the gate's lane taken and the tips read again, the slow gate run on the proving tip and joined with the fast run on record, then a plain fast-forward of the base branch — asked of its runner through `Proving`. afkconvoy's `promote` implements it with its lanes, its lock and its gate runner, and keeps what is the fleet's: the answer, the repair issue and the fleet's log. The crate's `Promoter` implements it by plain git and tells its program's forge how a promotion ended (`Forge::promoted`).

**Host kit** (`crates/host-kit`, `afkconvoy-host-kit`). What the host kit does to a machine. On the fleet's machines it gives every harness the shell finds the operator's **agent setup**: the instructions file linked at each harness's global instructions location, the declared skill list installed for each harness's agent and read-only between syncs, and the guards wired into each harness's own hook settings, only the kit's own entries replaced; and it says where the machine differs. sunfmin/dotfiles only declares the content — instructions file, skill list, guard programs — none of which names a harness; where each harness reads it is the harness crate's, and what is done there is this crate's, so a harness added to the kit needs no change to dotfiles. A guard is kept below the harnesses where it can be: read-only skills replace a hook that guarded them. Where the declaration is named, what was given is recorded and how a difference is reported are the embedder's (afkconvoy's host settings, `agent-setup.json`, a `doctor` finding naming `afkconvoy kit`). Guild uses the crate for `tmux` alone (sunfmin/control#780): its instances are not given the operator's setup; they start from factory engines and grow their own skills.

**Daybook** (`crates/daybook`, `afkconvoy-daybook`). Guild's daemon writes the daybook too (ADR-0065), so the entry's one shape (repo, kind of session, then `Did`, `Why`, `Undo`, `Lesson`, `Links`), the day's title in the host's local time, and `lesson_of` are spelled once: an entry written by either program reads, indexes and distills the same. The crate reads no environment variable of afkconvoy's nor its checkout list; telling the kind of session and the tracker stay the cli's, as does the weekly distillation's file. Its store today is a tracker's Discussions, one discussion a day, reached through the `GraphQl` seam, where of two discussions of one day the lowest numbered wins. ADR-0118 moves a host's daybook to `daybook.db` on the host, with both stores behind one interface; that is not built yet — the crate still writes Discussions alone.

**Host reading** (`crates/host-reading`, `afkconvoy-host-reading`), on the gate crate. How busy a host is — the kernel's CPU ticks over the last minute, the load average over the cores where those cannot be read, and the memory free under a floor its caller names — which the exclusive queue's holder starts a command by (ADR-0088) and admission reads (ADR-0107). Guild's daemon embeds the gate crate's holder and must read its host from the same code: two readers of the kernel's ticks would drift. It is not in the gate crate because it is foreign calls to the kernel, of which a Flux refinement says nothing. It runs `sysctl` by `PATH`, so a test world's stand-in still answers.

The local tracker (`crates/issues`, ADR-0091) is on the same terms.

## Considered options

- **Let the other program depend on afkconvoy-core.** Refused: the core's types named the issue, the role, the claim and the team, so a caller would build fleet values to start a session or queue a command, and every change to the fleet's types would reach it.
- **Copy the modules into the other program.** Refused: the rules would have two homes, and drift.
- **Move afkconvoy's own runners (gate, turn) into the crates too.** Not now: their lanes, process groups, freezing and adoption are a fleet host's. Each crate holds every rule its runner follows and a plain runner beside it.
- **Give the agent setup through a Claude Code plugin, chezmoi, or an installer of dotfiles' own.** Refused: a plugin reaches Claude Code alone; chezmoi or an installer would be a second place that knows where each harness reads, beside the host kit. A global `core.hooksPath` for a guard on `git push` would override every repo's own hooks, and was not taken.
