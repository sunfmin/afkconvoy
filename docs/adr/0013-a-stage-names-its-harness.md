# A stage names its harness, and a role carries each harness's limits

Until now every worker of a bound repo was a Claude Code session, and the fleet's start of a worker was written in Claude Code's flags, hooks and paths (ADR-0009). A team should be able to put one stage on another harness — pi is the first — to have work done, or reviewed, by something other than what wrote it.

A stage, and a patrol, names the harness its worker runs, beside its model. One that names none takes the default, which the project's config names; a config that names none means Claude Code. A consult and a landing run on the default. The former proposal worker was retired by ADR-0039. The worker starts in its role's directory whatever its harness (ADR-0009 holds), except Grok, which starts in the worktree (ADR-0043). The fleet adds, per harness, what that harness does not load from there.

A role has one core every harness works under: its rules and its skills, each written once. What a harness needs of its own is added to that core and never stands in its place. A role's limits are the part that cannot be shared, so they are written once per harness, in that harness's own form. The guard is the fleet's and not a role's: it is decided in one place for every harness, and each harness is given a way to ask it.

## Considered options

- **One harness for a fleet instance, chosen where it is started.** Smaller, and a team would name no harness. Refused: the reason to want a second harness is to set it against the first within one workflow, and which harness did the work changes the result, so it belongs in what is committed and not in how one host was started.
- **A role that names no harness, its files translated by the fleet.** One layout, and a stage's harness could change without touching a role. Refused with the next.
- **A role's limits written once and bridged.** The fleet would read a role's Claude Code hooks and run them for another harness. That makes the fleet the loader ADR-0009 was written to avoid, and a bridge that carries some hooks and silently drops the rest is worse for a limit than a refusal.
- **Model names a team writes once, mapped to each harness.** A table to keep, and one more place where which model ran is hidden.

## Consequences

- A limit a role holds under two harnesses is written twice. The fleet's check can tell that a role holds limits for a stage's harness; it cannot tell that they refuse the same things. A stage whose role holds limits for another harness and none for its own is refused, so a harness is never changed into fewer limits unseen.
- A team's files name harnesses, and a role's repo may hold files for more than one. A role is right for the harnesses its files cover and no others.
- A stage's model is passed as written and is its harness's own name for it. A team that names models and no harness is written for one default, and a repo that binds it under another is told so before a worker is started.
- A fleet instance has a worker launch command for each harness its workers run. Which harness is committed; how one is started stays the host's. A start that cannot start every harness it could be asked for is refused: none is ever stood in for by another.
- A worker loads nothing of the host user's configuration under any harness — but, since ADR-0017, their skills and rules, unless its team turns them off. For a harness with no way to say so, the fleet keeps a user directory of its own for it, holding only what the host knows of providers. That directory is not all a harness reads of the host user's: pi takes skills from the home directory wherever its user directory is, so the start also leaves skill discovery out and names the role's skills.
- A Codex worker loads the skills of the host user's home (`~/.agents/skills`): the one exception to the line above. Codex finds skills in `.agents/skills` and `.codex/skills` of the directory it starts in, in its user directory, among those it carries, and in `$HOME/.agents/skills` wherever its user directory is; it has no flag and no key that adds a directory of skills or leaves a whole one out. What it can be told to leave out is left out: the skills it carries. The home's are let be: the one way to keep them out is to start a worker under a home that is not the host user's, and the fleet does not work around a harness that way. So a Codex worker may be shown, beside its role's skills, ones that differ from host to host; a stage's `do` still names the role's.
- A role's skills are written once, where Claude Code finds them, and Codex does not look there. The fleet's copy of a role that a Codex worker starts in holds a link from where Codex looks to the role's skills, made once with the copy: a role's repo holds nothing for Codex. A role that holds a directory of skills for Codex itself is not refused and is left as it is; `check` notes a stage whose skill Codex would then not find.
- What the fleet's user directory holds of the host's is linked to, not copied: a login a harness renews is written where the host user's own is, so neither goes stale, and a file the user no longer has is gone from the directory at the next start. What the fleet itself gives a harness — the extension through which pi asks the guard — is kept there too, and named on the line that starts a worker, not left for the harness to find: a worker whose guard is missing does not start.
- Kimi Code reads hooks only from its user configuration, so a role's `.kimi-code/limits.toml` cannot be loaded in place. Each Kimi worker gets a role-specific `KIMI_CODE_HOME` in the fleet's cache: the fleet generates its `config.toml` from only the host's provider/model routing, the role's native Kimi hooks and permission rules, and the fleet's guard and orca report. A generated `SYSTEM.md` carries the repo and team rules; an `AGENTS.md` link in the role copy carries the role's. Credentials are linked, never copied; user hooks, MCP servers, plugins and other settings are not inherited. Separate homes keep concurrent roles from overwriting one another's limits. Generic `~/.agents` instructions and skills remain visible to Kimi wherever its data home is, as Codex's home skills are; explicitly named role skills take precedence where Kimi resolves duplicates.
- Grok's limits for a role are `.grok/config.toml`, hooks and the permissions it denies. A project file loads those denies and does not load hooks, so each Grok worker gets a role-specific `GROK_HOME` whose generated `config.toml` holds the role's hooks and denies, the fleet's guard and orca's report. Claude and Cursor hook and MCP compatibility are off, so `.claude/settings.json` and `.cursor/hooks.json` are not a second set of limits. The role's `CLAUDE.md` and `.claude/skills` stay where every harness writes them and are not copied into the worktree. Grok 1.0.60 and later reject `--add-dir`, so the worker starts in the worktree (ADR-0043): those rules are written into the home's `rules/told.md` with the repo's and the team's, and the skills directory is named in that home so a skill of the host user's of the same name does not stand in its place. Trust is `--trust` on the line that starts the worker, not a write to the user's trusted-folders file; `--help` on 1.0.70 does not name `--trust`, so the flag check does not require it. The guard is a `PreToolUse` hook that exits 2, and a guard that cannot be asked is refused the same way. The host user's skills and rules are given unless `host_user` is false; their hooks, MCP servers, plugins, permission mode and memories are not. The login is linked (`auth.json`), not copied. An unbound worker, and a watch, is the stock command plus `--trust` and the model flag, with no role, no role limits and no guard, using the host user's own Grok home.
- A harness that asks before it loads a role's own files is answered on the line that starts it, never at its terminal. The worker backend knows Claude Code's question and not pi's, and a role's limits in pi's form are not loaded until it is answered.
- A worker's stage record names the harness it ran on. It cannot be worked out from the commits the record already carries, since the default is the project's.
- An unbound repo's workers now run the first eligible harness of its host kit, with casting choosing the model within it (ADR-0020). Its worker launch command otherwise stays opaque, except for the model and every harness's worktree-trust setup. A Codex worker outside a role — the train worker too — is also given the fleet's own user directory, linking the host user's login, skills and rules. It keeps memories and bundled skills off as a role's worker does, but loads the repo's rules normally from the worktree and adds no role, team, stage facts or guard. Trust is launch configuration for every worker on every harness, never an entry added to the host user's config and never an answer typed at the terminal. A trust question that still appears is that harness's trust gap, reported with its command and worktree instead of retried as a failed dispatch. The command's flags are checked before these starts too.
