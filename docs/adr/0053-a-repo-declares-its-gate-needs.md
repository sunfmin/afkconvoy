# A repo declares its gate needs

For sunfmin/control#443, a repo declares the host requirements of its gate in a `yaml gate-needs` block. Each named check runs with `sh -e` in the checkout and has a time limit. The startup probe refuses a host when a check fails. A passing check stands for an hour; a running fleet instance checks again and ends broken when one fails. A changed declaration is checked immediately. Older releases read past the separate block, so they can still read the config during rollout.

A check can read secrets. Its stdout is discarded. On failure, only the last 20 lines of stderr are kept in a user-only file in the host cache, outside the checkout. The next run overwrites or removes that file. Refusals and doctor name the check, status, file and command to fix it, never its output. This follows the operator's ruling on the issue: plan, tick logs, doctor and issues may be copied away from the host.

For sunfmin/control#444, a repo may also declare `yaml cut-needs` checks in the same form. A due cut's checks run on this host before it claims the cut; a failure leaves it for another host and is named by the tick, plan and doctor. Checks run again before the claim, and use the same output privacy rules, with separate host-cache files. A repo without cut needs cuts as before. For sunfmin/control#532, a tick says the cut needs as the evaluation it starts the cut by: where its start of a cut checks them again, that check replaces the rebuild's look in the tick line, its answer and the log, so no tick both names a failed need and starts the cut. Doctor names a failed need's status and its stderr file on the host, never its output.

For sunfmin/control#570, a held cut is one condition, whichever of its needs fails first. A look checks every cut need, not only up to the first that fails, and names each that fails now. Their stderr lines go to one user-only file of the checkout's held cut, written again at each look that finds a need failing and removed only by one that finds none, so the file a finding names stands while the finding does. Doctor's `cut-need` finding is keyed by the checkout and the version the cut is due for — past its newest tag, or the declared initial one — not by the failing need: a cut held first by one need and then by another starts no new watch round.

For sunfmin/control#499, a gate or cut need may declare its install: `install`, with its limit `install_seconds`. Where the check fails, the host runs the install with `sh -e` in the checkout, through the host's exclusive queue as a heavy command, within its limit, then runs the check again. A pass admits; a fail refuses naming the check, the install's status and its stderr file. The install keeps the same output privacy as a check: stdout discarded, the last 20 stderr lines in a user-only host-cache file. A failed install is noted on the host and not run again for an hour, unless the declaration changes, which is tried at once, so no loop spends a host. A running fleet instance's hourly recheck installs the same way before it ends broken; a due cut installs before it is claimed. The startup probe, `plan` and `doctor` say when an install ran, how long it took and its result. A check without `install` refuses as before.

For sunfmin/control#574, a need is the host's wherever it is set off: its check and its install run with the host's environment — a fresh login shell's, as the host runner has it — never with the sandbox of the worker whose command started them. A worker's `plan` had run an install with its sandbox's dead proxy and scratchpad `TMPDIR`; it failed, and the host was noted as unable to install. A failed install a worker's command set off is not noted on the host, since the sandbox may still hold it whatever environment it is given; the host runner's own look installs and notes.

This came after sunfmin/control#495 and #497 locked two fleets for hours on a host that lacked a pinned toolchain another host had, while the workers rightly stopped: a large download needed the owner's consent. The owner now gives that consent, standing, for exactly this — "what a repo declares as a gate or cut need, at the version it pins, installed under the user's home. Anything else still asks first." So an install's contract is: it writes only under the user's home, never to system directories and never with sudo, and installs the pinned versions the repo already names, reading them from where the repo keeps them, not from a copy. afkconvoy runs the declared command and cannot check what it writes; keeping to the contract is the repo's.
