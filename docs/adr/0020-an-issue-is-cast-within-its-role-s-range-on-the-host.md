# An issue is cast within its role's range on the host

ADR-0013 had a stage name its harness and model, and the config name a default. Which harness and model suit a piece of work depends on the issue — how hard it is and what kind of work it is — more than on the stage it is at, and a stage cannot know that when the team is written. And which harnesses and models can run at all is a fact of each host: what is installed, logged in, and answering.

So the choice is made per issue, inside bounds two places set:

- A team's **roster** lists, for each role, the harnesses and models its workers may run, in order of preference, with what each model is good at and how to cast among them. It is committed with the team, as ADR-0013 wanted which harness does the work to be.
- A host's **host kit** lists the harnesses and models it can start now — each harness's worker launch command and each model seen to answer — and the harness and model of the stock consult. It is written with no human: `afkconvoy kit`, or `run` on a host without one, at a terminal or not, finds each harness installed in the shell a worker gets, has it list its models, sends each model a prompt, and keeps those that answered — the harnesses it held in their order, new ones after them in a fixed order of harnesses, each one's models in the order it lists them, and the stock consult where it is still held. After probes, one headless research session on the host kit's first has fifteen minutes to search primary and high-trust sources for new answered identities alone, under all their names: strengths and weaknesses as coding agents, dated source URLs, and harness and model preference order. Its checked JSON answer supplies `good_at`, `sources`, `researched_at` and order; missing or unsourced models are `not researched` and keep their fixed place, while an invalid answer or timeout keeps the fixed order and held research, saying why. The kit is written either way. A model held before keeps its research indefinitely, including across harnesses with the same id without a provider prefix; an alias now answering as another model is new. No new identity means no research session, including during daily refresh. Nobody is asked, and nothing is confirmed: one way writes the host kit, and `run` never refuses for want of one. It is never pushed. It stays current with no human: once a day a tick writes it again, adding a model a harness now lists once it answers its probe and dropping one it no longer lists; one fleet of the host does it, under a lock beside the file, and the others read the file. A refresh never drops what stops answering: a harness that stops working is paused on the host and left out of it until a probe finds it working again.
- A role's **range** on a host is its roster entry cut to the host kit, in the roster's order, less each harness the role holds no limits for while it holds limits for another: no worker of the role runs a harness it holds no limits for, and a host kit may hold everything its host can start. `check` and `plan` name each harness a range leaves out, and why. An unbound repo has no team and ranges over the host kit whole.

An issue's **casting** is its `harness:` and `model:` labels, the model in the harness's own name. A stage whose range holds the casting runs it; one whose range does not runs its range's first; a range of one leaves nothing to choose. An issue none of whose stages has a choice to make is not cast. One that has, and carries a flow label and no casting, is cast by a **caster**: a worker in no role, started by a tick that finds such an issue on the frontier and none running, which casts every such issue of the repo in one session and says on each why. The tick holds those issues back while it runs, for ten minutes at most, and dispatches them uncast after that. A human's labels are never recast; a casting no stage's range holds is not followed — each stage runs its range's first, `plan` says `unmatched`, and the issue is told once — for a name that matches nothing never stops work. Issues cast to a harness that is paused are cast again.

## Host priority and fault continuation (control #19)

Supersedes the earlier repository-local switch choice and the preference ordering above. Harness priority has one home: the order of the host kit. `switch --harness X` moves an existing entry first, preserving its command, models and probe evidence and the relative order of the rest. It runs without a checkout or instance. There is no separate chosen-harness record, repository mapping, clear operation or saved previous order. Old git-directory choices are neither read nor migrated. Kit writes reconcile with the latest order under the same mutation lock as promotion, so research or probes already in flight cannot overwrite a switch. Research ranks models, never harnesses.

Every issue, stage, consult, patrol, landing, caster and inspection selects the first eligible harness in kit order. Role support and limits remain constraints. Ticket casting, roster preference and stock-consult preference cannot select a later harness; matching model preferences only apply within the selected harness. Startability faults are skipped and explained, not passed off as a successful preferred launch. Team and ticket data are unchanged.

No running worker is interrupted by changing priority alone. `--all` continues workers across the host's checkout list, collecting failures while processing the rest. Continuation keeps the scene and breaker counts. Before another writer starts, terminal closure, runtime reports and the old process tree are checked; uncertainty leaves no second writer.

Worker health is evidence, not priority: observations and scoped faults live in the host cache, shared by its fleets and retained across runner restarts. Structured quota/authentication/disable, model and session errors retain their scope. A transient rate limit waits for its retry time and has two retries before session fallback. A screen alone goes first to another available kit harness for a tool-free diagnosis. The diagnosis returns a checked structured judgment with quoted evidence and missing information; it cannot perform recovery itself. Unknown, malformed or timed-out judgments preserve the scene. Silence never certifies an account fault.

Observation begins after a worker stops reporting progress. Two observations span at least 300 seconds; known background work and declared verdicts are excluded. Diagnosis has 30 seconds per candidate, three attempts per unchanged episode, and at least 300 seconds between attempts. Candidate account/model recovery probes run hourly, and only successful probes restore availability. Diagnostic failures try subsequent eligible harnesses; no candidate means waiting. A recovered preference participates in new starts without moving healthy successors back. Plan, doctor, panel and the tick log expose evidence, diagnosis source, scope, next check, action and actual successor.

## Considered options

- **Keep a stage's harness and model as an override.** Two places would decide which harness runs, and a wrong one would be looked for in both. A role that must run on one harness is given a range of one.
- **The roster on each host.** Which harness does the work changes the result, so it belongs with the team on every host, not with whichever host started the worker; what a host adds is only what it has.
- **A caster's judgement at each start, kept nowhere.** Not reviewable, paid again at every stage, and different from one start to the next. A label is on the issue, where a human sees and changes it.
- **One casting label per role.** Exact, but twice the labels and harder to read; in practice one step chooses and the rest are held to one harness.

## Consequences

- Supersedes ADR-0013's first paragraph: a stage, a patrol and the config name no harness or model, and `check` and `run` refuse a team file or a config that still does, saying what to delete and what the roster says instead. ADR-0013's other half stands: a role writes its limits once per harness, and a role's range leaves out a harness it has no limits for. A range left empty refuses no start: no worker of that role runs without its limits, so its stages wait while it lasts, and every other stage goes on. A roster entry that matches nothing in the host kit is not followed: the role ranges as if the roster named none for it. `check` still refuses a roster entry that names such a harness: those are the team's own words.
- `--worker-command` is gone: a harness's worker launch command is in the host kit.
- In an unbound repo the fleet now appends a harness's model flag to the worker launch command when an issue's casting names a model; with none, the command is still started as written.
- A team's roster is drafted by a command, from the host kit, into the team's working tree, and committed by a human; the fleet never changes it.
- ADR-0008 left out a stage choosing a later stage's model; the caster chooses for an issue's stages before any starts, which is that, and is now in.
